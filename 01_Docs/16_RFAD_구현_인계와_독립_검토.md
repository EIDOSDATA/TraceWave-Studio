# 설계 검토, 사용자 승인과 개발 인계

개정: 3.0 / 2026-11-07 KST / 상태: 사용자 검토용 설계안

## 1. 이번 작업의 경계

사용자는 모든 문서를 검토한 뒤 개발에 착수한다고 명시했다. 따라서 현재 산출물은 설계 문서와 변경/미결 기록이다. 이 문서의 미래 구현 지시나 과거 문구를 근거로 사용자 검토 전에 설치, prototype, 제품 코드, R0 해석을 자동 시작하지 않는다.

GUI 후보는 wxWidgets/Avalonia이고 Qt 계열은 제외한다. 낮은 메모리와 빠른 반응을 판단하는 측정 계획은 24번에 있다. 기본 기술 방향은 제안이며 실제 버전 조합, 성능과 solver capability는 후속 시험으로 고정한다.

## 2. 검토 순서

00/25의 변경 요약 -> 01/24의 범위와 GUI/성능 -> 03/17의 요구와 AC -> 04/05/06의 동작 -> 07/08/11의 구조와 계약 -> 09/10/13/22의 물리와 연산 -> 12/14의 출력과 검증 -> 15의 개발 순서다. 18/20/21/23은 근거, 데이터, 예시와 원문을 확인할 때 함께 읽는다.

## 3. D0 설계 검토의 종료 기준

| 관점 | 확인 내용 |
| --- | --- |
| 요구 | 141개 요구와 404개 AC의 안정 ID/의미 보존, B 128개 연결, AUG 4 반영 |
| 범위 | core stage와 강화 clause의 단계 구분, 2D/실제 STEP/물성/EM 요구 보존 |
| 물리 | 단위, phasor/Fourier, RMS, 전력 기준, complex Z0, 정의역과 특이점 |
| CAD | 원호 폭/반경, 층 Z, 실제 동박/중공 비아, 공차와 topology 왕복 검사 |
| 계약 | em_prepare/em_analysis, 불변 plan, 결과 조회/재처리, 오류/취소/복구 |
| 성능 | 상주 비용, 전체 worker 메모리, 입력 지연, cold/warm, 가상화/수명/상한 |
| 근거 | 실제 존재하는 파일, 출처의 확인 범위, 미실행 시험과 합격 기록 구분 |
| 추적 | AC -> VT/subcase -> 판정 대상 -> 필수 증거, 혼합 단계와 AND 판정 |

소프트웨어 실행이 필요한 항목은 입력 fixture, 측정법, 합격 규칙과 담당 역할을 정의하면 설계상 인계할 수 있다. 시험을 아직 하지 않았다는 이유로 수치를 만들어 채우지 않는다. 반대로 문서에서 결정 가능한 API/상태/단위 충돌을 단순 '추후 확인'으로 미루지 않는다.

## 4. 승인과 변경 기록

사용자가 검토할 결정은 [25번](25_RFAD_문서_검토와_승인.md)의 DEC-D0 표에 모은다. 승인 기록에는 문서 commit 또는 파일 hash 집합, 승인 날짜, 범위, 조건, 남은 결정이 필요하다. 현재 상태는 검토 대기이며 이 문서 작성 자체는 사용자 승인으로 간주하지 않는다.

실험 전 GUI를 최종 고를 필요는 없다. 두 후보와 측정 계획을 승인한 뒤 작은 비교 실험을 수행하고 결과로 하나를 선정할 수 있다. 기능/성능 예산을 변경할 때에는 이전 값, 근거, 요구/화면/API/VT 영향, migration/cache 무효화 영향을 기록한다.

## 5. 승인 이후 후속 작업자에게 전달할 계약

후속 작업자는 승인된 기준선을 읽고 실제 저장소/도구 상태를 먼저 확인한다. R0 작업은 15번 WBS 순서를 따르며 원문 요구와 ID를 편의상 삭제하지 않는다. 단위/표현식/snapshot, 정확한 기하, physical STEP, 실제 native solver와 정규화/수렴을 작은 기준 사례에서 연결한다.

GUI 비교는 24번의 동일 fixture, Release 설정과 원시 측정 기록을 사용한다. Python backend와 heavy worker 비용도 포함한다. 선정 전 두 완성 UI를 만들지 않고 선정된 한 toolkit만 제품으로 유지한다. mock은 UI/계약시험용으로 명시하고 현재 설계의 RF 결과로 표시하지 않는다.

새 실행 기록은 실제 만들어진 시점에만 문서와 연결한다. 현재 없는 과거 review/registry를 생성된 사실처럼 인용하지 않는다. 결과에는 입력/프로그램 버전과 hash, native 종료, 수렴, 물리 진단, target/출력/측정 상태를 독립 저장한다.

## 6. 수정과 이슈 관리

각 이슈는 ID, 관련 문서/requirement/AC/EQ/VT, 재현 조건, 근거, 영향, 수정, 남은 시험, 상태를 가진다. '문서 수정 완료'와 '실행 검증 통과'를 구별한다. critical 수식/단위/출력 손상/근거 없는 결과 경로는 검증된 기능으로 노출하지 않는다.

B의 잠정 숫자와 이번 성능 budget은 provenance가 있는 제안값이다. 적용 fixture/측정 오차/host 없이 전 제품 보장값으로 확대하지 않는다. 실제 장비나 원본 자료가 필요한 공백은 필요한 입력과 종료 조건을 적고, 확보 전까지 관련 기능을 제한한다.

코드 작성 시 한국어 Doxygen 주석, BSD/Allman 배치와 4칸 들여쓰기, 조건/반복문 중괄호 생략 금지를 따른다. 문서는 한국어와 키보드로 입력 가능한 문장부호/수식 표기를 기본으로 한다. 원본 B와 과거 source 식별자의 내용은 원본 보존을 위해 임의 정정하지 않고 현 설계의 해석을 별도로 기록한다.
