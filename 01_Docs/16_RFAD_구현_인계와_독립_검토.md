# 설계 검토, 사용자 승인과 개발 인계

개정: 3.4 / 2026-11-07 KST / 상태: 설계 기준선 승인 / 개발: 착수 전

## 1. 이번 작업의 경계

사용자는 2026-11-07 설계 기준선 3.4를 승인하고 문서 최신화와 커밋/푸시를 지시했다. D0 문서 승인은 완료되었으며 현재 산출물은 승인된 문서, 변경/미결 및 인계 기록이다. 이후 개발에 들어간다는 지시의 경계를 유지하며 별도 개발 착수 지시 전에는 설치, prototype, 제품 코드, R0 해석을 자동 시작하지 않는다.

GUI는 C++ wxWidgets로 확정되었고 상태는 `selected_pending_validation`이다. 일반 편집 60 fps/대형 장면 30 fps를 포함한 24번 PERF-001~010 및 기준 host/fixture는 초기 목표로 채택되었다. 유료 GUI 부품은 필수로 요구하지 않는다. Avalonia는 과거 비교 검토 자료로 보존하고 Qt 계열은 제외한다. 실제 버전 조합, 성능 합격과 solver capability는 후속 시험으로 확인한다. 정확한 CPU/GPU와 실행 manifest는 미정이며 초기 목표 채택은 최소사양 보장이나 실측 합격이 아니다. 3.4 전체 기준선은 승인되었고 실제 시험 및 개발 착수는 별도로 관리한다.

R1 최초 사용자 환경은 Windows 11 x64 wxMSW GUI와 local WSL2 Linux worker다. Linux native/headless worker의 R0 기본 계산 검증은 유지한다. Linux desktop wxGTK GUI 제품 수용은 출시 버전 미정의 후속 범위이며 자동으로 R2에 배정하지 않는다. R1은 원호/IFA 단일포트, 물성/급전/환경, 실제 2D/STEP/CAM, 기본 측정/스윕 및 전력/방사 검증을 포함한다. 내부 검증용 배포를 우선하며 외부 공개/상용 배포/소스 공개 방침은 후속 결정이다.

## 2. 검토 순서

00/25의 변경 요약 -> 01/24의 범위와 GUI/성능 -> 03/17의 요구와 AC -> 04/05/06의 동작 -> 07/08/11의 구조와 계약 -> 09/10/13/22의 물리와 연산 -> 12/14의 출력과 검증 -> 15의 개발 순서다. 18/20/21/23은 근거, 데이터, 예시와 원문을 확인할 때 함께 읽는다.

## 3. D0 설계 검토의 종료 기준

| 관점 | 확인 내용 |
| --- | --- |
| 요구 | 141개 요구와 404개 AC의 안정 ID/의미 보존, B 128개 연결, AUG 4 반영 |
| 범위 | core stage와 강화 clause의 단계 구분, 2D/실제 STEP/물성/EM 요구 보존 |
| 물리 | 단위, phasor/Fourier, RMS, 전력 기준, complex Z0, 정의역과 특이점 |
| CAD | 원호 폭/반경, 층 Z, 실제 동박/중공 비아, 공차와 topology 왕복 검사 |
| 계약 | em_prepare/em_analysis, 불변 plan, 결과 조회/재처리, 오류/취소/복구 |
| 성능 | 상주 비용, 전체 worker 메모리, 입력 지연, cold/warm, 가상화/수명/상한 |
| 근거 | 실제 존재하는 파일, 출처의 확인 범위, 미실행 시험과 합격 기록 구분 |
| 추적 | AC -> VT/subcase -> 판정 대상 -> 필수 증거, 혼합 단계와 AND 판정 |

소프트웨어 실행이 필요한 항목은 입력 fixture, 측정법, 합격 규칙과 담당 역할을 정의하면 설계상 인계할 수 있다. 실물 물성, 시험 PC의 정확한 모델, 실행 버전과 장비의 미확정 상태를 모두 해소해야 전체 개발에 착수할 수 있는 것으로 해석하지 않는다. 각 값은 해당 실행/비교/제작/배포 전에 고정하며 관련 검증이 미완료이면 그 범위의 합격을 주장하지 않는다. 시험을 아직 하지 않았다는 이유로 수치를 만들어 채우지 않는다. 반대로 문서에서 결정 가능한 API/상태/단위 충돌을 단순 '추후 확인'으로 미루지 않는다.

## 4. 승인과 변경 기록

사용자가 확정한 결정과 계속 검토할 결정은 [25번](25_RFAD_문서_검토와_승인.md)의 DEC-D0 표에서 구분한다. 승인 기록에는 문서 commit 또는 파일 hash 집합, 승인 날짜, 범위, 조건, 남은 결정이 필요하다. C++ wxWidgets와 유료 GUI 부품 비필수 방침, 성능 초기 목표/기준 host/fixture, R1 Windows 우선 범위, 첫 검증 순서 및 내부 검증용 배포가 확정되었다. 최초 IFA의 대역/외형/적층 목표/급전 초기 조건과 미결 항목의 처리 방향도 채택되었다. 정확한 실행 manifest, 실제 재료 물성과 상세 형상/제작/측정은 개발 중 해당 작업 전에 확정할 기술 입력이며, Linux GUI 출시와 외부 공개/상용/소스 공개는 후속 출시 전에 결정한다. 처리 시점과 담당 역할은 [25번 미결 항목 처리 기준](25_RFAD_문서_검토와_승인.md#remaining-decision-policy)을 따른다. 전체 문서 기준선 승인은 2026-11-07 완료되었고 별도 개발 착수 지시만 대기 상태다. 승인 기록과 파일 식별자는 [25번 기준선 승인 기록](25_RFAD_문서_검토와_승인.md#baseline-approval)에 연결한다. 문서 버전 3.4를 유지하고 승인 상태 반영본과 사용자가 검토한 승인 전 내용의 해시를 구분해 보존한다.

GUI-SPIKE-001~007은 확정된 wxWidgets의 통합/성능/배포 검증으로 수행하며 후보 선택을 다시 요구하지 않는다. 일반 편집과 대형 장면의 frame 목표 및 검수 설계 기준은 24번 PERF-006을 따른다. 기술 선택이나 기능/성능 기준을 변경해야 하면 기존 사용자 결정, 변경 이유, 요구/화면/API/VT 영향, migration/cache 무효화 영향을 기록하고 결정 범위를 명시한다. 성능 미달을 근거로 확정된 60 fps/30 fps 목표를 조용히 완화하지 않는다.

## 5. 개발 착수 지시 후 작업자에게 전달할 계약

후속 작업자는 별도 개발 착수 지시를 받은 뒤 승인된 기준선과 실제 저장소/도구 상태를 먼저 확인한다. R0 작업은 15번 WBS 순서를 따르며 원문 요구와 ID를 편의상 삭제하지 않는다. 단위/표현식/snapshot, 정확한 기하, physical STEP, 실제 native solver와 정규화/수렴을 완전한 참조 계산 사례에서 먼저 검증한다. 이어 물성이 완비된 단일포트 IFA를 첫 제품 사례로 진행하고 R1 원호도 별도로 검증한다. 최초 IFA는 [21번 IFA 초기 검증 기준](21_RFAD_사례와_계약.md#ifa-initial-baseline)을 따르며 대역/외형/적층 목표/급전 초기 조건은 채택되었다. 실제 재료 물성과 상세 제작/측정 조건은 후속 확정한다. 물성은 사용자 입력/자료 선택 변수로 유지하고 가정값 기반 탐색 결과를 실물 검증 완료로 승격하지 않는다. G031은 기하 전용이며 원본의 미정 물성/적층/환경을 임의로 채워 실제 RF 기준으로 승격하지 않는다.

wxWidgets 통합 검증은 24번의 고정 fixture, Release 설정과 원시 측정 기록을 사용한다. Python backend와 heavy worker 비용도 포함한다. 일반 편집 60 fps/대형 장면 30 fps는 실제 화면 변경 중 측정하며 idle 60 fps 강제 redraw loop로 구현하지 않는다. 유료 GUI 부품은 필수 의존성으로 요구하지 않으며 이 방침을 유료 부품 일체 금지나 제품 무료 배포로 해석하지 않는다. mock은 UI/계약시험용으로 명시하고 현재 설계의 RF 결과로 표시하지 않는다.

새 실행 기록은 실제 만들어진 시점에만 문서와 연결한다. 현재 없는 과거 review/registry를 생성된 사실처럼 인용하지 않는다. 결과에는 입력/프로그램 버전과 hash, native 종료, 수렴, 물리 진단, target/출력/측정 상태를 독립 저장한다.

## 6. 수정과 이슈 관리

각 이슈는 ID, 관련 문서/requirement/AC/EQ/VT, 재현 조건, 근거, 영향, 수정, 남은 시험, 상태를 가진다. '문서 수정 완료'와 '실행 검증 통과'를 구별한다. critical 수식/단위/출력 손상/근거 없는 결과 경로는 검증된 기능으로 노출하지 않는다.

B 원문의 잠정 숫자는 역사적 제안으로 보존한다. 이와 별도로 24번의 PERF-001~010과 기준 host/fixture는 현재 초기 목표로 채택되었다. 초기 목표는 실측 합격이나 최소사양 보장을 뜻하지 않으며 정확한 CPU/GPU, OS/driver, 측정 오차와 실행 manifest를 고정한 뒤 검증한다. 실제 장비나 원본 자료가 필요한 공백은 필요한 입력과 종료 조건을 적고, 확보 전까지 영향을 받는 실물 검증/해당 capability의 합격 범위만 제한한다. 독립적으로 가능한 편집/저장/가정 모델 탐색이나 다른 구현 작업은 진행할 수 있다. 원본 A 복구 자체는 전체 개발의 선행조건이 아니며 회복 후 충돌이 확인되면 영향 요구와 기능을 재검토한다. 내부 검증용 배포도 의존성과 원문의 라이선스/권리 기록을 생략하는 근거가 아니다.

코드 작성 시 한국어 Doxygen 주석, BSD/Allman 배치와 4칸 들여쓰기, 조건/반복문 중괄호 생략 금지를 따른다. 문서는 한국어와 키보드로 입력 가능한 문장부호/수식 표기를 기본으로 한다. 원본 B와 과거 source 식별자의 내용은 원본 보존을 위해 임의 정정하지 않고 현 설계의 해석을 별도로 기록한다.
