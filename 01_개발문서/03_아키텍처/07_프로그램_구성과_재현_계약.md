# 프로그램 구성과 재현 계약

새 구현에서 프로젝트를 한 번 편집하고 저장한 뒤 서비스가 종료되어도 같은 개정과 해석 원본을 열 수 있어야 한다. 이 문서는 그 동작을 만드는 순서와 관찰값을 설명한다. 설치 환경과 컴파일 명령은 [개발 실행 안내](../../Code/README.md), 84개 화면의 배치와 조작은 [화면 목록](../04_화면설계/README.md)에서 찾는다.

## 1. 프로세스 연결과 기능 조회

Windows의 Studio는 C++ wxMSW 앱이다. 앱이 Python 서비스를 자식 프로세스로 시작하고, 서비스가 프로젝트 작업 영역의 유일한 쓰기 잠금을 잡는다. GUI가 준비해야 하는 절대 경로는 앱 서비스의 Python, 소스, 작업 영역이다. CAD와 도면 출력에는 각 전용 Python 경로를 추가한다. 기본 해석 연결은 서비스가 감사된 Windows openEMS 설치에서 찾는다. 연결에 실패하면 편집과 이전 결과 읽기는 계속 제공하고 해석 시작은 사용할 수 없다고 표시한다. [GUI 시작 인자](../../Code/ui/wxwidgets/main.cpp), [서비스 시작](../../Code/src/rfad/__main__.py), [해석 환경 선택](../../Code/src/rfad/application/solver_runtime.py)

첫 요청은 다음 한 줄이다. UTF-8 JSON 뒤에 LF 한 바이트를 보낸다. 응답은 stdout에서 같은 요청 ID로 읽고 운영 로그는 stderr에서 읽는다.

```json
{"jsonrpc":"2.0","id":1,"method":"capabilities.get","params":{"contract_version":"rfad.api/2.0","context":{},"input":{}}}
```

작업 영역을 열면 응답의 `profile`은 `rfad.projects/0.2`다. `methods`와 개별 기능의 상태를 확인하고 `idempotency_policy.request_key_epoch`를 변경 요청에 사용한다. 작업 영역 없이 시작한 `rfad.bootstrap/0.1`은 조회 전용이다. 한 프레임은 최대 1 MiB이고 한 배치의 요청은 최대 16개다. 큰 데이터는 파일 참조나 페이지로 받는다. [RPC 계약과 응답 생성](../../Code/src/rfad/application/rpc.py), [GUI 전송과 큐](../../Code/ui/wxwidgets/service_client.cpp)

## 2. 한 프로젝트의 생성, 변경, 복구

다음 순서의 변수는 직전 응답에서 가져온다. 읽기 요청의 `params`는 위 예처럼 구성하고 변경 요청에는 새 `request_key`와 현재 `request_key_epoch`를 추가한다. 프로젝트를 대상으로 하는 요청에는 `context.project_id`에 생성 결과의 ID를 넣는다.

| 호출 | 입력과 처리 | 확인할 결과 |
| --- | --- | --- |
| `project.open` | 빈 문맥에서 `{"path":"projects/예제","open_mode":"create","name":"예제"}`를 보낸다. | 접수 응답의 `job_id`로 `job.status`를 빈 문맥에서 조회한다. 완료 이벤트의 `operation_result`에서 `project_id`, `revision_id`를 읽는다. |
| `project.apply_command` | `expected_revision`에 위 개정, `command_id`에 새 UUID, `type`에 `metadata.rename`, `payload`에 `{"name":"변경한 이름"}`을 보낸다. | 직접 응답의 `new_revision`을 기록한다. 보낸 것과 같은 epoch, 키, 메서드, 문맥과 본문으로 재전송하면 같은 응답과 개정이다. |
| `snapshot.create`, `project.save` | 각각 새로운 요청 키와 같은 `expected_revision`으로 요청하고 두 작업의 종료를 각각 조회한다. | 스냅샷에는 불변 파일 참조가, 저장 결과에는 `saved_revision`이 있다. 사용자의 후속 편집은 새 개정에 기록한다. |
| 서비스 재시작 후 `project.open` | 같은 작업 영역을 열고 `{"path":"projects/예제","open_mode":"recover"}`를 보낸다. | 복구된 이름과 저장 개정이 일치하고 스냅샷 파일의 바이트가 같다. 이전 변경 요청을 영수증 유효 기간 안에 그대로 보내도 이름 변경은 한 번만 반영된다. |

저장소에 실제로 쓰는 순서도 이 동작의 일부다. 먼저 전체 원본을 검증하고 정규 바이트를 `projects/<이름>/revisions/<개정 UUID>/project.json`에 한 번 쓴다. 다음으로 새 상태와 그 파일 참조가 담긴 manifest를 `commits/<커밋 UUID>` 안에 쓴다. 파일을 다시 읽어 확인한 뒤 같은 볼륨의 `current.json` 포인터를 원자적으로 교체한다. 포인터를 게시하기 전에 종료되면 이전 커밋이 기준이다. 미게시 파일을 발견했다는 이유만으로 복구 시 현재 개정을 바꾸지 않는다. [저장 순서](../../Code/src/rfad/storage/journal.py), [명령과 영수증](../05_기능설계/01_프로젝트/01_프로젝트_명령과_저장.md)

프로젝트 원본은 `rfad.project/0.6`으로 쓴다. 0.1~0.5의 봉인본은 원래 바이트로 읽고 다음 편집에서 새 개정을 만든다. 파일 참조의 `sha256`은 실제 파일 바이트에 대한 해시다. 정규 내용 해시에는 UTF-8의 `rfad.canonical/1.0`과 줄바꿈을 앞에 붙인다. 같은 내용이라도 해시의 용도에 맞는 입력을 사용한다. [정규 인코딩](../../Code/src/rfad/application/canonical.py), [파일 참조와 개정 검사](../../Code/src/rfad/application/project_repository.py)

## 3. 고정한 설계로 계산하고 결과 열기

1. 현재 설계를 스냅샷으로 고정한다. `solver.plan`에 스냅샷 ID와 내용 해시, 해석 프로필과 조건을 보낸다. `runtime_profile="auto"`이면 현재 연결한 해석기를 쓴다. `solver.prepare`는 계획 ID와 내용 해시를 받아 입력 파일을 준비한다. 실제 계산은 준비가 끝난 계획으로 `job.submit`을 호출할 때 시작한다. 필드와 실행 예산은 [해석 요청 계약](../05_기능설계/04_해석결과/02_해석작업_계약.md)에 있다.
2. 작업은 `queued`에서 시작한다. 준비, 실제 실행, 후처리를 각각 해당 상태로 기록하고 `job.status`에서 마지막 커서 이후의 이벤트를 읽는다. 취소 의도를 게시한 뒤에는 늦게 도착한 완료 통지가 이전 상태를 덮어쓸 수 없다. 실제 종료를 확인해야 `cancelled`가 된다. 실행한 설계와 그 뒤에 편집한 설계는 원래 스냅샷 ID로 구별한다. [상태 전이표](04_형상과_해석작업_모듈구조.md), [Windows 프로세스 감독](../../Code/src/rfad/application/windows_solver_process.py)
3. 결과 창은 목록의 출처를 선택해 `result.describe`를 호출한다. 읽은 `source`와 `pin={identity_hash,dataset_sha256}`을 다음 표본, 차트, 비교, 내보내기 요청에 다시 보낸다. 원문이 바뀌면 조회를 중단한다. 공통 복소 투영을 제공하지 않는 해석 프로필은 원래 해석 결과 조회를 사용한다. 개발 PC에서 검증한 파일 교환 범위와 실제 9포트 해석을 구분한다. [다중 결과 계약](../05_기능설계/04_해석결과/07_다중결과와_방사표시.md), [9포트 실계산](../07_검증/410_아홉_급전과_분포_모드_원문_검증.md)
4. GUI는 선택 세대와 프로젝트가 일치할 때 응답을 표시한다. 네트워크, Smith, 방사, 필드 등 상세 탭은 처음 열 때 만들고 다시 열 때 재사용한다. 화면에 표시할 개정 이름은 읽기 응답에서 꾸민다. 기존 `pin`을 만드는 개정 레이블과 내보내기 메타데이터의 바이트는 호환 대상이다. [결과 컨트롤러](../../Code/ui/wxwidgets/result_workspace.cpp), [해시와 표시 이름](../../Code/src/rfad/application/result_sources.py), [첫 화면 계측](../07_검증/423_알원_사용성_후속_수정과_재검수.md)

## 4. 재현을 확인하는 시험

저장소 루트에서 시작한다. 아래 시험은 임시 작업 영역과 자체 입력을 사용한다. 기존 사용자 프로젝트를 경로로 넘길 필요가 없다. Windows x64용 CPython 3.12를 사용한다. 결과 원본 시험은 HDF5를 생성하므로 고정 수치 환경도 필요하다. 첫 실행에서는 아래와 같이 환경을 만들고 패키지 해시를 검사한다. 이미 준비된 환경은 마지막 세 줄로 시험할 수 있다.

```powershell
Set-Location Code
py -3.12 -m venv .local/rf-check
& ./.local/rf-check/Scripts/python.exe -m pip install --only-binary=:all: --require-hashes -r runtime_profiles/python-network-windows-x64.txt
$env:PYTHONPATH = 'src;tests'
py -3.12 -X utf8 -m unittest -v test_project_process test_job_state test_network_files
& ./.local/rf-check/Scripts/python.exe -X utf8 -m unittest -v test_result_sources
```

| 시험 | 통과하면 관찰한 내용 |
| --- | --- |
| [test_project_process](../../Code/tests/test_project_process.py) | 위 2절의 요청을 실제 별도 서비스 프로세스에 보내고 강제 종료 후 재시작해 응답, 개정, 스냅샷 바이트를 대조한다. |
| [test_job_state](../../Code/tests/test_job_state.py) | 취소 의도나 종료 상태 뒤에 도착한 응답을 거절하고 작업 ID와 이벤트 순번을 보존한다. |
| [test_network_files](../../Code/tests/test_network_files.py) | 비대칭 행렬의 입출력 포트 순서, 파일 원문 조건, CSV 열 대응, 표본과 크기 경계를 확인한다. |
| [test_result_sources](../../Code/tests/test_result_sources.py) | 과거 개정의 원문과 내보내기, 사라진 현재 자료, 혼합된 목록 페이지, 잘못된 소유자와 변조된 고정 해시를 확인한다. |

실제 계산 환경에는 [Windows 해석기 실행과 취소](../07_검증/417_윈도우_기본_해석과_설치_검증.md), 제조 교환에는 [기판 원문과 제조 파일 계약](../05_기능설계/05_출력교환/05_기판형상과_제조파일_교환.md)을 추가 적용한다. 최종 배포 수용에는 [R1 수신 검수](../09_개발계획/04_현행버전_남은작업.md)의 별도 Windows PC가 필요하다.
