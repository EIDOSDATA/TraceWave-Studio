| 영역 | 담당 내용 | 적용 규칙 |
| --- | --- | --- |
| `00_참고자료` | 레퍼런스 원문, 수집/추출 자료와 기존 근거 기록 | 내부 폴더명/파일명/내용을 변경하지 않는다. 사용자 복구 상태를 유지하며 개발 문서 규칙으로 재정리하지 않는다. |

## 권위와 목적

사용자의 승인 방향과 RFAD-D0-3.4의 요구/수용 기준을 유지한다. 현재 기능 계약은 실제 지원 동작을 정의하고 승인 요구와의 간극을 표시한다. 구현이 제한되어 있다는 이유로 승인 요구를 삭제하거나 완료 기준을 완화하지 않는다. 새로운 제안은 `설계안/미구현/검증 대기`로 표시한다.

## 중복과 불필요한 내용

현재 API/수량/자원 제한은 기능 계약 또는 공통 명세 한 곳이 소유한다. 상위 안내는 짧은 요약과 링크를 제공한다. 서로 다른 문서가 같은 기능의 현재 상태를 다르게 설명하면 실제 코드/지원표를 확인해 현재형을 교정한다. 과거 날짜 아래의 `미구현` 문구는 그 시점 기록임을 명확히 한다.

버려진 제안은 현행 읽기 순서에서 빼고 archive로 분류한다. 원문/추출/검증 사본의 중복은 출처나 이력의 연결이 다를 수 있어 파일 hash만으로 삭제하지 않는다. 불필요한 반복이나 잘못된 현재 설명을 정리한 내역은 review에 기록한다. 불필요한 중복 진입 파일은 삭제한다. 승인 근거와 과거 실행 파일은 이력으로 보존한다.

## 기능 구현 전 문서의 준비 조건

기능마다 목적, 지원 범위/제외 범위, 원본/DTO/파일의 소유자, 단위/상태/출처, 명령/역명령/버전, 정상/취소/실패/결과 불명, 화면/사용자 행동, 유한 자원 및 호환/검증 기준을 적는다. 이미 승인된 상세 수식/지원 범위는 해당 승인 UI/FN/API/EQ로 연결하고 비슷한 새 정의를 복제하지 않는다.

결정할 수 있는 UI/소프트웨어 정책은 문서에서 구체적으로 정한다. 실제 납품 물성/시료/교정/독립 비교/성능 수치는 필요한 증거와 확인 시점을 명시하고 미정으로 남긴다. 미정을 숨겨 문서상의 설계 완료를 만들지 않는다. 승인 문서가 있다고 해서 wire 필드나 capability가 이미 구현되었다고 가정하지 않는다.

## 변경과 검수

1. 담당 계약과 화면설계서를 먼저 수정하고 연결 UI/FN/API/기존 개발 단계를 기록한다.
2. 서비스/표시 모델/View를 분리해 구현하며 문서와 실제 동작의 차이를 갱신한다.
3. 필요한 회귀와 실제 GUI 시나리오를 실행한다. 문서만 바꾸면 링크/그림/내용 일치 검수만 새 증거로 기록한다.
4. `check_documents.py`, 필요한 경우 구현 감사 생성/`--check`로 링크와 추적을 확인한다.
5. 검토를 마친 작업 단위마다 한국어 커밋/푸시한다. 기존 미완료 작업은 섞어 완료 처리하지 않는다.

개발 문서의 폴더/파일 이동 때에는 상대 링크, 감사 JSON의 근거 경로, 안내 README와 문서 경로 대응표를 같이 갱신한다. 이 절차를 참고자료 내부에 적용하지 않는다. 과거 runtime profile 안의 경로는 당시 소스 식별의 일부이므로 고치지 않는다. 문서 도구는 제품 GUI나 사용자 프로젝트를 수정하지 않는다.

모든 개발 문서와 그림의 정식 위치는 저장소 `01_개발문서`다. Code/docs에는 별도 사본이나 전달 파일을 유지하지 않는다. Code/README와 제품 하위 README는 빌드/실행 진입 안내이며 상세 계약은 01_개발문서로 연결한다. 문서 통합/편집은 2026-11-16 사용자 지시에 따른 것이며 새 RFAD 기준선 승인으로 간주하지 않는다.

## 폴더와 파일 이름 규칙

`01_개발문서`의 모든 폴더와 파일은 `숫자번호_한글명` 형식으로 관리한다. 각 폴더 안에서 01부터 새로 번호를 매기며 기존 RFAD 문서 26개도 파일명 정리 대상이다. 폴더는 `01_요구사항`, 문서는 `01_문서명.md`처럼 쓴다. 그림/편집 원본, SVG/PNG, 기계 판독 JSON 등 확장자와 무관하게 같은 규칙을 적용한다. 파일명의 영문 주제 이름을 한글로 정리하되 문서 본문의 요구/FN/API/VT/EQ 등 안정 ID와 기술 식별자는 유지한다.

번호는 탐색 순서이며 기존 개발 단계 1~13이나 승인 문서의 내용 식별자를 다시 정의하지 않는다. 서로 연결된 Markdown/DrawIO/SVG/PNG 및 JSON의 관계는 현재 링크와 문서 목록에서 유지한다. 이름과 번호를 바꿀 때 전체 링크/도구 입력/감사 경로를 같이 갱신한다.

승인 기준선 보관함의 당시 원문/records도 한글 파일명과 새 번호로 배치한다. 단, 본문 바이트, 원래 해시와 manifest 안의 당시 경로/기록은 고치지 않는다. 보관본의 이전 경로와 현재 경로를 별도 대응표로 연결하여 원래 hash 검사를 수행한다. 승인 본문 안의 옛 상대 링크를 고치기 위해 원문을 다시 쓰지 않는다. 보관함 안내와 대응표가 원문 탐색을 제공한다.

예외와 보존 경계는 다음과 같다.

- `README.md`: 각 영역과 폴더의 진입 안내 이름을 유지한다.
- `Code`의 코드/빌드/시험/fixture/도구 파일: 개발 코드의 기존 경로와 형식을 따른다.
- `00_참고자료` 내부: 원문 묶음의 영문을 포함한 폴더명/파일명/상대 경로/manifest/출처 해시를 보존한다. 이름 변경, 이동, 내용 정리 대상이 아니다.
- 과거 `Code/runtime_profiles`: 당시 환경/소스/실행 증거의 위치와 파일명/내용을 보존한다.

사용자의 최종 지시에 따라 참고자료 내부 재배치는 철회되었다. 사용자가 복구한 참고자료를 다시 이동하거나, 내부 원문을 현재 문서 경로에 맞추어 수정하지 않는다. 새 문서 분류/명명 작업은 `01_개발문서`에서 수행한다.
