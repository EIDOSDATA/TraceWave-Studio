## 1. 검토 범위와 읽는 방법

승인 03/06/11/14/17의 실제 요구/기능/API/시험 전문과 Code의 domain/application/adapter/GUI 및 시험 본문을 대조했다. 현재 기능과 구체적인 누락을 [기능별 구현 대조](01_구현감사/04_기능구현대조.md)에 기록했다. 각 FN 아래에는 코드, 시험 메서드, 기존 실행 근거와 담당 단계가 있다.

[기계 판독 대조표](01_구현감사/03_구현추적.json)는 141개 요구, 404개 AC, 407개 검수 subcase, 46개 FN, 30개 VT와 30개 승인 API를 연결한다. DES-URS 5개, PERF 10개와 GUI-SPIKE 7개도 별도 보충 조건으로 보존한다. R1/R2/R3가 나뉜 subcase를 합쳐서 R1 완료로 바꾸지 않는다.

기능 상태는 partial(부분 구현), not_implemented(제품 기능 미구현), deferred(승인된 후속 범위)로 구분했다. 최초 대조는 부분 구현 23개, 미구현 13개, 후속 10개였다. 이 수치는 출시 완료율이 아니다. 이후 구현은 해당 FN과 근거를 갱신하고 기존 감사 기준 commit을 함께 남긴다.

목표 저장/명령/호환성 추가 때 부분 구현 24개, 미구현 12개, 후속 10개였다. 이후 목표 편집 GUI와 명시 치수 템플릿을 FN-004/006/007/008에 반영한 시점은 부분 구현 26개, 미구현 10개, 후속 10개였다. 연결/기본 DRC와 적층/외부 STEP 후속을 반영한 현재 원천 46개 FN의 집계는 부분 구현 28개, 미구현 8개, 후속 10개다. [목표 편집](../05_기능설계/02_설계편집/07_목표편집_서비스계약.md), [템플릿](../05_기능설계/02_설계편집/08_원호와_평면역에프_형상템플릿.md), [설계 규칙](../05_기능설계/02_설계편집/11_목표제약과_연결_설계규칙검사.md), [적층/환경](../05_기능설계/02_설계편집/12_적층과_외부환경.md)의 실제 범위만 반영했으며 전체 기능 수용이나 목표 성능 합격 수는 늘리지 않는다.

기존 단위/계약/native 시험의 통과는 연결한 범위의 증거다. 각 AC의 전체 조건과 필요한 실측/교환/성능 근거가 갖춰졌다는 정식 수용 판정을 이번에 새로 하지 않았으므로 acceptance_status=open으로 유지한다. 이는 이미 통과한 단위시험을 실패로 바꾼다는 뜻이 아니다. AC별 연결은 검수 대상을 찾는 색인이며 연결 FN의 시험을 모든 AC의 직접 검증으로 주장하지 않는다.

## 3. 공통 계약과 GUI 결정

[R1 공통 구현 계약](../02_시스템명세/08_공통구현_계약.md)에 원본 소유권, 버전/호환, 요청 멱등성, 작업/판정 상태, 결과/연구 DTO, cache/무효화와 출력 계약을 확정했다. 구현에서 필요한 최소 확장만 하며 승인 요구를 현재 코드의 제한에 맞춰 축소하지 않는다.

[Studio GUI 설계](../04_화면설계/08_스튜디오_화면계약.md)는 가독성/편의성, native 입력과 Studio 작업 공간, 테마/아이콘/DPI/키보드/오류 안내를 정한다. 기존 조사 도구와 개발 환경의 적용 요소를 비교하고 실제 기능/성능 검수와 구분한다. 기능을 구현할 때 화면을 함께 연결하고 12번에서 전체 사용 흐름을 다시 검수한다.

## 4. 검증과 재현

```powershell
.\.venv\Scripts\python.exe -X utf8 tools/build_implementation_audit.py --check
```

도구는 요구/AC/subcase 수와 고유성, 정확한 VT/API/보충 조건 ID 집합, 요구-AC-VT 연결, subcase의 AC/단계 귀속과 API capability ID를 검사한다. FN별 코드/시험/근거 파일, 지정한 Python 시험 심볼, 생성기/검토 입력 및 UTF-8 본문 hash도 기록한다. 임시 workspace에서 worker를 시작하지 않고 실제 capabilities를 읽어 승인 API 30개의 등록 상태를 비교한다. 원문 문서나 사용자 프로젝트를 변경하지 않는다.

검토된 JSON 입력을 변경한 뒤 산출물 갱신은 --check 없이 실행한다. 생성/검사 성공은 문서 추적의 무결성이고 물리/성능 수용시험 통과가 아니다. 기존 runtime_profiles는 당시 실행의 증거로 보존하며 문서 변경으로 다시 작성하지 않는다.

생성/재현 검사는 통과했다. `tests/test_implementation_audit.py`의 12개 시험은 잘못 연결된 동일 개수 자료, 누락 심볼, 본문/산출물 변조를 차단하는지 확인했다. 이번 제품/GUI 검증 범위와 별도 실행 시점은 [개발 상태](../09_개발계획/02_개발착수와_현재상태.md)의 최신 기록을 따른다.

3번 설계 모델 보강의 첫 구현 시점에는 여러 목표 대역과 명시한 성능 한계를 기존 명령/undo/영수증/저장/재열기에 연결했다. 목표 입력은 미평가 상태이며 자동 solver 설정이나 물리 성능 판정과 혼동하지 않는다. 뒤이어 [원호/IFA 템플릿 계약](../05_기능설계/02_설계편집/08_원호와_평면역에프_형상템플릿.md)과 [목표/템플릿 화면](../04_화면설계/10_목표와_형상템플릿_화면.md)을 연결했다. 이 최초 시점에 남아 있던 문헌 카드/초기 후보와 연결/기본 검사는 이후 아래 문헌 구현 및 2026-11-16의 설계 규칙/환경 후속에 반영했다. 일반 RF 자동 합성과 정밀 편집 전체 수용은 여전히 남아 있다. 최초 [제안 문서](../12_보관이력/02_초기제안/01_형상템플릿_최초제안.md)는 이력으로 보존한다.

G031 문헌 카드의 원문 archive/member/좌표 및 가정, 수정값/배치/부분 기하와 검증 축을 기존 후보/원자 적용/GUI에 연결했다. [문헌 카드 계약](../05_기능설계/02_설계편집/09_문헌기반_부분기하_카드.md)의 실제 지원만 FN-006/007에 반영한다. 전체 보드 재현, 초기 RF 합성, 해석/실측 합격이나 3/4번 전체 완료로 확대하지 않는다.
