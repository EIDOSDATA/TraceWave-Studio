## 복원과 재생

검수 작업 영역을 새 경로에 풀고 파일별 해시를 대조했다. `rfad serve`의 `result.describe`와 `result.page`에서 기존 원본 pin과 8~12 GHz 표본 31개를 읽었다. 설치본 `tools/mcp_stdio.py`의 동일 조회는 공개 API와 같은 응답을 반환했다. 원본의 저장 개정과 결과 ID는 고정 목록에 기록했다. ZIP 안의 초기 작업 영역을 새 경로로 풀면 같은 조회를 다시 실행할 수 있다. [실행 기록](429_알원_알시십_클린피시_실행기록.json)

### 비교 작업 사본 만들기

Windows의 저장소 루트에서 실제 보존 ZIP과 새 출력 경로를 지정한다. 출력 경로의 상위 폴더는 미리 준비한다.

```powershell
$archive = 'C:\검수자료\TraceWave-Studio_R1_B0_보존.zip'
$output = 'C:\검수자료\B0-대조'
py -3.12 -X utf8 Code/tools/restore_b0_proof.py '01_개발문서/07_검증/431_알원_비제로_고정목록.json' $archive $output
```

도구는 보존 ZIP과 431에 열거된 멤버의 크기 및 SHA-256을 확인한다. 작업 파일 850개를 새 `B0`와 `main` 폴더에 복원하고 사본의 파일별 해시를 대조한다. 공개 API 및 MCP 원본은 `protocol`에, 해시 기록은 `restore-verification.json`에 둔다. 각 서비스는 그 서비스에 해당하는 사본을 사용한다. [복원 도구](../../Code/tools/restore_b0_proof.py)

### 저장 개정과 결과 재생

복원 직후 사본을 사용한다. CPython 3.12와 고정 RF 패키지가 설치된 Python 실행 경로와 검증한 RC10 배포본의 `Code` 경로를 지정한다.

```powershell
$manifest = '01_개발문서/07_검증/431_알원_비제로_고정목록.json'
$python = 'C:\검수자료\rf-venv\Scripts\python.exe'
$b0Code = 'C:\검수자료\RC10\Code'
& $python -X utf8 Code/tools/replay_b0_result.py $manifest $output $b0Code > (Join-Path $output 'replay-results.json')
```

재생 도구는 저장 개정과 문서 SHA-256, 원래 결과의 출처와 pin, 주파수 및 dB 표본, 두 런타임의 공개 API와 MCP 동등성을 검사한다. 조회 전후에는 잠금 파일을 제외한 작업 파일의 해시를 대조한다. 성공한 JSON 보고서에는 결과 설명과 표본 응답을 기록한다. 보존한 API와 MCP 원본은 해시를 검증하고 아래 절차에서 보고서의 응답과 대조한다. [결과 재생 도구](../../Code/tools/replay_b0_result.py)

1. 검증한 RC10 배포본에는 `B0` 작업 사본을, 현재 소스에는 `main` 작업 사본을 지정한다. 각 배포본에서 `python -m rfad serve --workspace <사본 경로>`를 실행한다. 공개 API 서버를 종료한 뒤 같은 사본으로 `python tools/mcp_stdio.py --workspace <사본 경로>`를 실행한다. API 호스트는 각 배포본의 `Code/src`를 사용한다.
2. `431.replay.project_id`의 저장 개정과 저장 문서 SHA-256을 `saved_revision`, `saved_sha256`과 대조한다. `result.describe`에서 `context.project_id`와 `input.source`를 지정한다. `input.source`의 `kind`는 `solver`이고 `artifact_id`는 `431.replay.result_artifact_id`다. 응답의 `pin`과 출처를 `431.replay.result_pin` 및 `protocol/B0-public-api.json`의 동결 응답과 대조한다.
3. 같은 출처로 `result.page`를 조회한다. `input`에 동결 `pin`, `row=0`, `column=0`, `offset=0`, `limit=201`을 전달한다. `page.samples`에는 8~12 GHz의 표본 31개가 있어야 한다. 모든 `frequency_hz`와 `magnitude_db`를 동결 API 응답 및 시제품의 표본과 binary64 단위로 대조한다. [시제품에 기록한 S11 표본](../../Code/ui/prototype/b0_samples.h)
4. MCP의 `initialize`와 `notifications/initialized` 뒤 `tools/call`의 `name`으로 위 두 메서드를 사용한다. `arguments`에 API와 같은 `context`와 `input`을 전달한다. `isError`가 `false`이고 `structuredContent`가 API의 `result` 및 `protocol/B0-mcp.json`의 동결 응답과 일치하는지 확인한다. 공개 API 계약, MCP 프로토콜 및 도구 수는 431의 고정값과 대조한다.
5. 조회 검수를 기록한 뒤 사본에서 편집 성공, 오래된 개정의 `E_CONFLICT`, 동일 요청 키의 재시도를 대조한다. 편집 개정의 ID는 각 사본에서 새로 생성되므로 입력 개정과 결과 개정의 관계를 확인한다. `capabilities.get`에서 Windows 해석 런타임 `openems-windows-x64/0.1`을 확인하고, 실행 중 `job.cancel`을 빈 `context`와 해당 `input.job_id`로 호출한다. 작업이 `cancelled`이고 `termination_confirmed`가 `true`인지 확인한 뒤 기존 결과를 다시 연다.

실지원 환경은 Windows 11 x64와 기본 Windows openEMS다. 제작 물성, 실물 측정 및 별도 배포 정책은 각 사례의 기존 상태를 따른다. 리팩토링 착수는 후속 작업에서 결정한다. [지원 범위](../08_운영환경/06_내부검증_지원범위와_미결.md) [이식 계획](../09_개발계획/07_현행버전_완료후_리팩토링.md)
