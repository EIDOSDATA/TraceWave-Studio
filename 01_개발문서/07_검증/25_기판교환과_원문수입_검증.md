# 기판 교환과 원문 수입 검증

작성일: 2026-11-17 KST. 완료 계획 10번 가운데 기판 모델 0.6, 기계 형상, PCB/CAM 파일과 원문 수입의 유한 지원 범위다. 자동 시험, 실제 Windows GUI 회귀와 수동 화면 검수, 저장/재열기 확인을 마쳤다. 최초 실패와 후속 보완, 최종 서비스 변경 후 집중 시험을 아래에서 실행별로 구분한다. 이 기록을 전체 UX 또는 제조/실측 수용 완료로 확대하지 않는다.

[기능 계약](../05_기능설계/05_출력교환/05_기판형상과_제조파일_교환.md), [화면 계약](../04_화면설계/25_기판교환과_원문수입_화면.md), [실행 기록](26_기판교환과_원문수입_실행기록.json), [개발 완료 계획](../09_개발계획/03_개발완료_계획.md)을 함께 읽는다. 기준 커밋은 `de8b5ac8ca5cfc47d955e557bc76b07e12919e23`이다. 이전 도면/STEP 기록, 승인 기준선, 참고자료 및 84개 시안은 소급 수정하지 않는다.

## 1. 확인한 구현 범위

`rfad.project/0.6`의 선택적 `pcb`와 `board.cutouts`에 내부 절삭, NPTH/직선 슬롯, 명시 도금 홀, 풋프린트 소유와 핀, 제조 개구, 금지 영역, 수입 원문 연결을 보존한다. 이전 0.1~0.5 문서는 읽기만으로 변경하지 않으며 처음 변경한 명령에서 승격한다. 처음 없던 컨테이너는 실행 취소 때 다시 없어진다. 풋프린트 멤버의 세계 좌표가 권위 원본이고 이동/회전은 한 번만 적용한다. 자동 수정 상태와 원래 이름/출처는 같은 역명령으로 복원한다.

공통 SI 투영을 실제 CAD, 도면, DRC와 파일 교환에 연결했다. 내부 절삭과 홀을 실제 제거한 뒤 도체 연결을 검사하고, 기존 단일 객체 표현으로 연결 성분을 확정하지 못하는 경우에는 미평가로 남긴다. 기계 형상을 실제로 소비하지 않는 EM 경로는 사전 검사에서 차단한다.

닫힌 profile의 KiCad 보드/풋프린트, Gerber X2, XNC와 기본 Gerber Job을 별도 교환 worker에서 생성하고 다시 읽는다. 고정 snapshot, 전체 원문 sidecar, 파일별 hash, reader 범위와 누락/미지원 항목을 보존한다. 새 검수는 원래 출력 패키지를 덮어쓰지 않는다. 교환 라이브러리는 host 서비스에서 직접 실행하지 않는다.

가져오기는 파일 경로/바이트 수/hash를 먼저 선언하고 최대 256 KiB 청크를 순서대로 확인한다. 실제 parser 결과의 층/넷, 기판, 독립 풋프린트 배치와 손실 항목을 사용자가 명시적으로 대응한 뒤 단일 typed 명령으로 적용한다. 원문 40개와 보고서 1개, 합계 16 MiB를 넘는 수입은 명시 차단한다. 불명 요청은 기존 key/epoch 영수증으로 조회하며 미발견을 생성 부재로 단정하지 않는다.

## 2. 실제 형식과 보존 경계

- KiCad의 원래 세계 좌표와 아래면 방향을 두 번 변환하지 않는다. 도형을 담기 위한 `technical_container`는 실제 부품/핀으로 만들지 않고 원래 컨테이너와 자식의 바인딩을 남긴다.
- 현재 전체 도체 적층의 두 끝층을 명시한 관통 via는 전체 관통으로 연결한다. 없는 공구 지름, 도금 두께와 재료는 미정이다. 부분 적층을 전체 관통으로 추정하지 않는다.
- 기존 기판 외곽을 1 nm 파일 좌표 정밀도로 대조한 뒤 분리된 내부 원/직선 폐곡선만 새 절삭으로 받는다. 열린 선, 접점, 교차, 중첩, 기존 절삭과의 중복 및 확정하지 못한 복합 원호는 자동 치유하거나 병합하지 않는다.
- `Soldermask`의 파일 `Negative`는 도막이 없는 개구 의미로 처리한다. 객체의 `LP clear` 합성과 구분한다. `Paste`의 명시 양극성과 실제 원형/직선 개구도 보존한다. 지원하지 않는 곡선 region을 다각형으로 조용히 근사하지 않는다.
- zone의 재채움/간격/열연결 정책과 미소비 token은 원문과 손실 보고서에 남긴다. 대응 가능한 명시 도체로 변환하더라도 외부 CAD의 zone 편집 규칙을 계승했다고 표시하지 않는다. 필요한 손실 확인이 없으면 적용하지 않는다.
- 새 수입 기록이 있는 연구 후보의 일반 사본 채택은 원문 파일 소유권 복사가 구현되지 않은 범위에서 명시 차단한다. 원문을 지우고 사본 생성을 성공시키지 않는다.

## 4. 실제 Windows 자동 검증

PCB 편집 폼에서는 신규 홀의 지름/공구/도금 미정을 확인한 뒤 0 지름을 명시 거절하고 유효한 1 mm 비도금 홀로 수정했다. 형상과 변경표가 실제로 보이며 변경 사유를 고치면 검토 hash가 무효화되는지 검사했다. 기존 홀의 이름 초안을 검토한 상태에서 지름 표시만 mm에서 um으로 바꾸어 1 mm가 1000 um으로 보이면서 원문 SI와 검토 결과는 그대로 유지되는지 확인했다. 이름 초안은 저장하지 않았다.

한 번 적용한 홀은 typed 선택과 한 개 undo 항목으로 연결됐다. 최초에 없던 `pcb` 컨테이너가 undo로 사라지고 redo로 정확히 복원됐다. 저장과 서비스 재시작 뒤 같은 원본을 읽었다. 실제 물리 설정의 미정 치수, 사용자 extension의 null/출처, 원래 형상/재료와 기존 파일 hash를 대조했다. 늦은 응답/창 파괴와 불명 영수증 key 유지도 별도 합성 gateway 경계로 확인했다.

교환 폼은 실제 CAM Job 생성과 새 검수를 수행했다. 별도 실제 writer에서 만든 KiCad 원문에 유효한 후행 공백을 더해 300 KiB 이상 원문을 두 청크로 전송하고 바이트/hash를 비교했다. 실제 parser 결과에 층/넷을 명시 대응하고 손실 항목을 확인한 뒤, 입력 변경에 따른 검토 무효화와 단일 적용을 검사했다. undo/redo, 저장/서비스 재시작 및 runtime 없는 조회에서 원문 파일, 기존 형상/재료/적층/전체 extensions와 과거 solver 결과를 보존했다.

이 자동 검증은 실제 native 컨트롤과 영속 원문의 범위다. 모든 화면의 수동 조작성이나 렌더 품질을 자동으로 합격 처리하지 않는다. 수동 화면 검수와 캡처 근거는 아래에서 자동 적용 시험과 별도로 구분한다.


실제 수동 검수에서는 기존 홀의 치수/공구 미정/출처 탭을 읽고 CAM Job을 생성한 뒤 별도 검수를 실행했다. 309107 bytes의 KiCad 원문을 두 청크로 보존하고 parser를 읽었으며 가져오기 네 탭과 필수 대응을 선택하지 않은 상태의 적용 비활성을 확인했다. 수동 가져오기 적용은 수행하지 않았다. 적용/undo/redo의 근거는 위의 별도 자동 10개 검사다.

저장 후 정상 종료하고 native runtime 없는 ProjectService로 재열어 전체 문서, 기존 파일 25개의 hash, 원문 bytes/hash, 형상/재료/적층/전체 extensions 및 공구 미정을 대조했다. 초기 보존 검사 스크립트는 source_files 포장 구조와 result_format 위치를 잘못 가정해 두 차례 실패했으며 실제 구조에 맞춘 뒤 성공했다. 이 검사 도구 오류를 제품 오류로 기재하지 않는다.

첫 수동 검수의 `767db6d1...`에서는 별도 CAM 재검수가 기술도면으로 분류되고 reader가 미기록으로 표시되는 문제를 발견했다. 표시를 보완한 `cb804d87...`로 교환/CAD 환경 없이 같은 workspace를 새로 열어 Gerber/드릴/Job 용도와 `bounded Gerber/XNC/Job parsers`를 확인했다. 기존 수입 원문 309107 bytes, hash와 읽기 완료 상태도 복원됐다. [실행 화면 51~61](02_실행화면/README.md)은 두 빌드의 시점을 구분한다. 51~59의 확장자는 실제 JPEG 형식에 맞게 정정했고 이동 전후 바이트 hash가 같았다.

## 5. 실제 KiCad 수신 검증

KiCad 10.0.8의 실제 CLI/pcbnew를 사용하여 파일을 읽고 zone을 다시 채운 뒤 저장했다. 원래 명시 도체의 합집합에서 원래 완성 홀/절삭을 뺀 영역과, 수신한 실제 pad/via/zone 도체에서 수신한 홀/절삭을 뺀 영역을 층/넷별로 대조했다. 도체 성분, 내부 구멍, 0.1 mm 열린 간격을 확인했다. 단일 `GetLayerName` 대신 실제 다층 `GetLayerSet().Seq()`를 검사했다.

Gerber 6.6 좌표의 1e-6 mm 양자화, 교환 경계 근사의 1e-5 mm chord, profile 경계 3e-5 mm와 실제 수신 refill 경계 0.001 mm는 각 비교의 수치 조건이다. 제조 공차나 RF 정확도 허용값이 아니다. 수신 시험의 0 간격/최소 폭 설정은 유한 합성 사례의 원래 기하를 비교하기 위한 명시 설정이며 생산 DRC 통과를 뜻하지 않는다.

## 6. 초기 실패와 후속 보완

첫 형식/수신 시험에서는 숫자만 사용한 zone net이 실제 KiCad에서 net 0으로 읽히는 문제를 발견해 이름을 포함한 문법으로 고쳤다. 실제 다층 패드의 단일 층 이름을 기대한 시험은 층 집합을 대조하도록 수정했다. C0 aperture, Gerber 시작점/보간 모드와 미소비 규칙을 명시하도록 reader도 보강했다.

가져오기 독립 리뷰에서 비부품 포장을 부품으로 만드는 문제, 두 끝층으로 표현된 4층 관통 via의 과도한 거절, 내부 절삭을 외곽에 섞어 거절하는 문제, mask 파일 극성과 paste 역할 불일치를 수정했다. 새 절삭 목록의 UUID 정렬 누락도 후속 시험에서 보완했다. 잘못된 합성 artifact 경로, 명시 G01/G05가 없는 시험 문자열, bytes 반환값 오해, 정렬되지 않은 시험 원본과 이전 스키마의 미래 버전 가정은 시험 오류로 구분했다.

첫 PCB 편집 GUI는 수정하지 않은 원본과 빈 사유의 preview가 적용 가능하다고 기대하여 단계 8에서 실패했다. 제품의 무변경 거절을 약화하지 않고 저장하지 않는 이름 초안에서 단위 표시만 검사하도록 시험을 고쳤다. 첫 교환 GUI 시도는 host 표시 DTO 편집 중 괄호 오타로 Python import에서 중단되어 GUI 창을 열지 못했다. 수정 후 전체 문법 검사와 집중 회귀를 거쳐 새 로그로 실행했다. 최초 로그/보고서를 삭제하거나 최종 성공으로 덮어쓰지 않았다.


전체 GUI 회귀의 기존 출력 시험 한 건은 표의 종류 이름을 `제외`로만 기대했으나 제품이 `제외 / 의미 보존 범위`로 구분하면서 실패했다. 제외 객체 이름과 `include_in_export=false` 원문 사유의 의미는 유지됐다. 기존 smoke의 정확한 기대 문구만 고친 뒤 새 바이너리로 출력 시험을 다시 실행했다. 최초 전체 회귀의 실패 수를 통과로 바꾸거나 전체를 최종 무실패로 표시하지 않는다.


전체 GUI가 끝난 뒤 저장 경계를 독립 검토하면서 저널의 남은 용량이 작은 합성 사례에서 완료 이벤트의 용량을 검사하기 전에 수입 보고서가 봉인되는 문제를 재현했다. 원래 프로젝트와 수입 원문은 손상되지 않았지만 참조되지 않는 보고서 파일이 남을 수 있었다. 일반 출력의 게시 전 검사를 공통화하고 수입에도 연결해 용량/취소/상태/nonce를 보고서 봉인 전에 확인하도록 보완했다. 이후 집중 31개와 실제 출력/수입 native 7개를 새 로그로 통과했다. 이 보완은 전체 GUI 이후의 서비스 변경이며 앞선 전체 회귀나 GUI가 최종 Python 소스를 실행했다고 표시하지 않는다.

## 7. 상태와 남은 수용 경계

- 수동 Windows 화면 검수, 정상 종료와 runtime 없는 재열기 보존 확인을 마쳤다. 수동 가져오기 적용은 수행하지 않았으며 자동 적용 검사와 구분한다.
- 정식 모델/교환 profile의 유한 부분을 지원한다. 모든 KiCad/Gerber/XNC 문법, 임의 macro/곡선 합성/복합 드릴 또는 외부 도구의 모든 편집 의미를 지원한다는 주장은 없다.
- 공구 지름, 도금 두께, 실제 물성과 제작/납품/측정 조건은 원문이 없으면 미정이다. 같은 형식 reader나 실제 수신 기하 대조가 제조 수용을 대신하지 않는다.
- 실제 EM 소비가 없는 기계 feature와 polygon 기판은 사전 차단한다. 기존 RO4350B 국부 방사 도체 손실 변화 2.788446%의 초기 2% 기준 미확립, GHz PTH 독립 정확도와 실측 검증 미확립을 유지한다.
- 이전 SOLIDWORKS 활성화 제한으로 수행하지 못한 독립 STEP 수신 검수는 이 단계의 KiCad 결과로 대체하지 않는다.
- 실행 소스는 HOST 192개/직렬화 2,068,702 bytes, EXCHANGE 23개/284,347 bytes로 192개/4 MiB 상한 안이다. 정확한 목록/hash는 기록 생성 시점으로 고정한다.
- 전체 84개 화면, 접근성, 성능, 포괄적 장애 복구 및 R1 최종 수용은 별도 미완료 항목이다.
