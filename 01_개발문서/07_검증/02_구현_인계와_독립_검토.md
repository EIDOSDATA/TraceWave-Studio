# 설계 검토, 사용자 승인과 개발 인계

현행 편집본 / 2026-11-25 / 근거 RFAD-D0-3.4 / 새 기준선 승인 아님

2026-11-07 승인 당시 내용과 승인 기록은 [기준선 보존본](../12_보관이력/01_승인기준선/01_삼점사/18_구현_인계와_독립_검토.md)으로 분리했다. 이 문서는 현재 구현과 남은 설계의 관계를 정리한 편집본이며, 문서 수정만으로 구현/시험 상태를 승격하지 않는다.

## 1. 현재 인계의 경계

사용자는 2026-11-07 설계 기준선 3.4를 승인했고 후속 지시로 제품 개발과 단계별 커밋/푸시를 진행했다. 2026-11-16에는 화면설계서와 전체 문서 검토/분류를 지시했으며, 이후 개발 문서를 `01_개발문서`에 통합하고 기존 문서도 검토/수정하도록 했다. 제품 코드는 `Code` 아래에 유지한다. 승인 당시 원문/기록과 현재 편집본은 분리하여 변경 이력을 추적한다.

GUI는 C++ wxWidgets를 사용한다. 실제 Windows 환경에서 입력과 접근성, 저장 및 복구를 확인한다. Qt 계열은 제외하며 기본 기능에 유료 GUI 부품을 요구하지 않는다. 기준 PC의 프레임, 지연 및 자원 성능 시험은 현행 R1 승인표에서 제외했다.

R1 기본 환경은 Windows 11 x64, wxMSW GUI와 Windows openEMS다. 기존 WSL2 해석기는 선택한 환경에서 재현한다. Linux native/headless worker의 R0 기본 계산 검증은 유지한다. Linux desktop wxGTK GUI 제품 수용은 출시 버전 미정의 후속 범위이며 자동으로 R2에 배정하지 않는다. R1은 원호/IFA 단일포트, 물성/급전/환경, 실제 2D/STEP/CAM, 기본 측정/스윕 및 전력/방사 검증을 포함한다. 각 후보의 소스 개정, 설치본 및 실행 근거는 [검증 안내](README.md)에 있다. 정식 상용 배포 방침은 별도 결정 사항이다.

## 2. 검토 순서

새 작업은 [개발 인계](../09_개발계획/08_새채팅_개발인계.md)와 [기능 개발 순서](../09_개발계획/15_기능채택과_개발검증_순서.md)에서 시작한다. 대상 기능의 [실행 기록](README.md), 기능 계약과 실제 코드를 대조한다. 화면 작업에는 [화면설계서](../04_화면설계/README.md)의 화면 ID/기능/전환/예외/접근성과 이름/선택 정책을 함께 적용한다. 승인 범위와 수용 조건은 01/03/14/17/24, 시스템은 04/07/08/11, 물리는 09/10/13/22, 근거는 18/20/21/23을 확인한다. 과거 승인 자체는 25의 기록과 보존본에서 확인한다.

## 3. D0 설계 검토의 종료 기준

| 관점 | 확인 내용 |
| --- | --- |
| 요구 | 141개 요구와 404개 AC의 안정 ID/의미 보존, B 128개 연결, AUG 4 반영 |
| 범위 | core stage와 강화 clause의 단계 구분, 2D/실제 STEP/물성/EM 요구 보존 |
| 물리 | 단위, phasor/Fourier, RMS, 전력 기준, complex Z0, 정의역과 특이점 |

| 계약 | em_prepare/em_analysis, 불변 plan, 결과 조회/재처리, 오류/취소/복구 |
| 성능 | 상주 비용, 전체 worker 메모리, 입력 지연, cold/warm, 가상화/수명/상한 |
| 근거 | 실제 존재하는 파일, 출처의 확인 범위, 미실행 시험과 합격 기록 구분 |
| 추적 | AC -> VT/subcase -> 판정 대상 -> 필수 증거, 혼합 단계와 AND 판정 |

소프트웨어 실행이 필요한 항목은 입력 fixture, 측정법, 합격 규칙과 담당 역할을 정의하면 설계상 인계할 수 있다. 실물 물성, 시험 PC의 정확한 모델, 실행 버전과 장비의 미확정 상태를 모두 해소해야 전체 개발에 착수할 수 있는 것으로 해석하지 않는다. 각 값은 해당 실행/비교/제작/배포 전에 고정하며 관련 검증이 미완료이면 그 범위의 합격을 주장하지 않는다. 시험을 아직 하지 않았다는 이유로 수치를 만들어 채우지 않는다. 반대로 문서에서 결정 가능한 API/상태/단위 충돌을 단순 '추후 확인'으로 미루지 않는다.

## 4. 승인과 변경 기록

사용자가 확정한 결정과 계속 검토할 결정은 [25번](05_문서_검토와_승인.md)의 DEC-D0 표에서 구분한다. 승인 기록에는 문서 commit 또는 파일 hash 집합, 승인 날짜, 범위, 조건, 남은 결정이 필요하다. C++ wxWidgets와 유료 GUI 부품 비필수 방침, 성능 초기 목표/기준 host/fixture, R1 Windows 우선 범위, 첫 검증 순서 및 내부 검증용 배포가 확정되었다. 최초 IFA의 대역/외형/적층 목표/급전 초기 조건과 미결 항목의 처리 방향도 채택되었다. 정확한 실행 manifest, 실제 재료 물성과 상세 형상/제작/측정은 개발 중 해당 작업 전에 확정할 기술 입력이며, Linux GUI 출시와 외부 공개/상용/소스 공개는 후속 출시 전에 결정한다. 처리 시점과 담당 역할은 [25번 미결 항목 처리 기준](05_문서_검토와_승인.md#remaining-decision-policy)을 따른다. 문서 기준선 승인은 2026-11-07 완료되었고 이후 개발 착수 지시도 이행 중이다. 현재 구현/검증 상태는 날짜별 개발 기록을 따른다. 승인 기록과 파일 식별자는 [25번 기준선 승인 기록](05_문서_검토와_승인.md#baseline-approval)에 연결한다. 기준선 ID와 당시 해시를 보존하며 현행 편집본에 원래 승인 해시가 그대로 적용된다고 표시하지 않는다.

GUI-SPIKE-001~007은 wxWidgets의 기능, 접근성, 수명 관리 및 배포 검수에 연결한다. 기술 선택이나 기능 기준이 바뀌면 변경 이유, 영향 요구와 기존 자료의 호환 범위를 기록한다.

## 5. 계속 작업할 개발자에게 전달할 계약

후속 작업자는 승인된 기준선과 현재 구현 계약, 실제 Git/도구 상태를 먼저 확인하고 기존 작업 트리 변경을 보존한다. 기존 1~13 완료 계획과 15번 WBS 선행관계를 함께 따르며 구현된 저장/명령/후보/GUI를 다시 만들거나 원문 요구와 ID를 편의상 삭제하지 않는다. 단위/표현식/snapshot, 정확한 기하, physical STEP, 실제 native solver와 정규화/수렴을 완전한 참조 계산 사례에서 먼저 검증한다. 이어 물성이 완비된 단일포트 IFA를 첫 제품 사례로 진행하고 R1 원호도 별도로 검증한다. 최초 IFA는 [21번 IFA 초기 검증 기준](04_사례와_계약.md#ifa-initial-baseline)을 따르며 대역/외형/적층 목표/급전 초기 조건은 채택되었다. 실제 재료 물성과 상세 제작/측정 조건은 후속 확정한다. 물성은 사용자 입력/자료 선택 변수로 유지하고 가정값 기반 탐색 결과를 실물 검증 완료로 승격하지 않는다. G031은 기하 전용이며 원본의 미정 물성/적층/환경을 임의로 채워 실제 RF 기준으로 승격하지 않는다.

wxWidgets 통합 검증은 24번의 고정 fixture, Release 설정과 원시 측정 기록을 사용한다. Python backend와 heavy worker 비용도 포함한다. 일반 편집 60 fps/대형 장면 30 fps는 실제 화면 변경 중 측정하며 idle 60 fps 강제 redraw loop로 구현하지 않는다. 유료 GUI 부품은 필수 의존성으로 요구하지 않으며 이 방침을 유료 부품 일체 금지나 제품 무료 배포로 해석하지 않는다. mock은 UI/계약시험용으로 명시하고 현재 설계의 RF 결과로 표시하지 않는다.

새 실행 기록은 실제 만들어진 시점에만 문서와 연결한다. 현재 없는 과거 review/registry를 생성된 사실처럼 인용하지 않는다. 결과에는 입력/프로그램 버전과 hash, native 종료, 수렴, 물리 진단, target/출력/측정 상태를 독립 저장한다.

## 6. 수정과 이슈 관리

각 이슈는 ID, 관련 문서/requirement/AC/EQ/VT, 재현 조건, 근거, 영향, 수정, 남은 시험, 상태를 가진다. '문서 수정 완료'와 '실행 검증 통과'를 구별한다. critical 수식/단위/출력 손상/근거 없는 결과 경로는 검증된 기능으로 노출하지 않는다.

B 원문의 잠정 숫자는 역사적 제안으로 보존한다. 실제 장비나 원본 자료가 필요한 공백은 필요한 입력과 종료 조건을 적고, 확보 전까지 영향을 받는 실물 검증/해당 capability의 합격 범위만 제한한다. 독립적으로 가능한 편집/저장/가정 모델 탐색이나 다른 구현 작업은 진행할 수 있다. 원본 A 복구 자체는 전체 개발의 선행조건이 아니며 회복 후 충돌이 확인되면 영향 요구와 기능을 재검토한다. 내부 검증용 배포도 의존성과 원문의 라이선스/권리 기록을 생략하는 근거가 아니다.

코드 작성 시 한국어 Doxygen 주석, BSD/Allman 배치와 4칸 들여쓰기, 조건/반복문 중괄호 생략 금지를 따른다. 문서는 한국어와 키보드로 입력 가능한 문장부호/수식 표기를 기본으로 한다. 원본 B와 과거 source 식별자의 내용은 원본 보존을 위해 임의 정정하지 않고 현 설계의 해석을 별도로 기록한다.

## 7. 현재 인계

1~7번은 공개 자료와 지원 모델에서 정한 내부 범위를 마감했다. 8번 RO4350B 고정 사례의 7/8분할 편차는 사용자가 허용했다. PTH 독립 손실 비교는 합성 급전과 접합 조건에 한정한다. 9번은 원호와 IFA 설치 후보의 격자와 외부 경계를 독립적으로 바꾼 모든 비교 조건에서 목표 대역을 충족했다. [격자별 손실 기록](307_팔분할_일반격자_손실_수렴검증.md), [접합과 급전 손실 대조](301_급전격자와_관통홀_표면손실_독립대조.md), [설치 후보의 대역 평가](311_설치후보_격자와_외부경계_대역검증.md)

10번은 같은 개정의 STEP, 도면과 CAM 수신 기록을 재사용한다. 11번은 자료가 있는 프로젝트에서 선택한다. 12번은 실제 Windows에서 한글 IME, 스크린리더와 혼합 DPI를 검수했다. 13번은 검수할 개정의 Setup.exe와 해시를 고정한 뒤 온라인 상태의 별도 클린 Windows 11 x64 PC에서 기본 설치, 예제 실행, 제거 및 재설치를 확인한다. [현행 작업표](../09_개발계획/04_현행버전_남은작업.md), [내부 후보의 지원 범위](../08_운영환경/06_내부검증_지원범위와_미결.md)
