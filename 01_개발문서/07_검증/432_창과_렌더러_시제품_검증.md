## Windows 분리 입력 창 이동과 IME 좌표 자동 시험

소스 개정은 `0402448c90f84f3aabc441ced0f4919c3b17965b`이고 실행 파일 SHA-256은 `93db62feb0043406e9854dccc016233ea9b06d14e90a536f8e3a0b901d80b346`이다. Windows 11 Pro x64, Intel Iris Xe bgfx Vulkan, 150% 화면에서 `ctest --test-dir Code/build/shell-prototype --output-on-failure -V --repeat until-fail:5`로 `prototype_window_smoke`를 연속 5회 통과했다.

- 본창의 입력란에 초점을 둔 뒤 SDL에 전달한 IME 위치는 창 내부 `(677,135)`였다.
- 분리 입력 창은 같은 모니터에서 `(816,514)`에서 `(880,514)`로 이동했다. SDL에 전달한 IME 위치는 이동 전후에 분리 창 내부 `(99,102)`였고 해당 창의 메모 캐럿과 일치했다.
- 이동한 분리 창에서 합성 조합, 취소, 확정을 검사했다. 분리 창을 닫은 뒤 본창으로 키보드 초점이 돌아왔고 IME 위치 `(737,135)`는 본창의 현재 메모 캐럿과 일치했다.
- 수동 검수용 시제품을 동시에 열고 실행한 두 번의 시험에서는 분리 창이 닫히고 본창 메모가 활성화됐으나 시험의 SDL 키보드 초점 검사가 실패했다. 수동 검수본을 종료한 뒤 실행한 연속 시험에서 초점 검사를 포함해 통과했다.

결과 재생 도구 작업에서 같은 SHA-256의 시제품을 다시 확인했다. 독립 실행 조건에서 같은 시험을 연속 5회 통과했다. 이번 장비에서는 두 번째 배율을 사용할 수 없어 그 항목은 건너뛰었다.

여기서 SDL의 창 이동 요청은 실제 창에 적용됐고 입력 이벤트는 합성했다. WIN32에서 보이는 실제 Microsoft 한자 후보창의 화면 위치는 아래 실기 검수에서 확인한다.

## 실제 Microsoft 입력기의 후보 목록 진단

`15a7cd6`의 시제품에 Win32 입력기 진단만 넣은 별도 검수본을 사용했다. 본창과 분리 창에서 Microsoft 한국어 입력기 `0412`를 활성화하고, Windows 키 입력 `g k s`로 `한`을 조합했다. 변환 요청을 예약해 추가 키를 누르지 않고 조합 문자열이 UTF-16 2바이트인 동안 `ImmSimulateHotKey(IME_KHOTKEY_HANJACONVERT)`와 `ImmNotifyIME(NI_OPENCANDIDATE)`를 각각 실행했다.

두 요청은 두 창에서 성공값을 반환했다. `ImmGetCandidateWindow`는 본창 `(817,135)`, 분리 창 `(51,102)` 등 각 창 내부에 설정된 후보 위치를 반환했다. `ImmGetCandidateListCountW`의 목록 수는 0이었고 화면에는 후보창이 나타나지 않았다. 물리 한자 키나 입력기 메뉴로 후보창을 여는 실기 판정은 남았다. [Windows IME 단축키 식별자](https://learn.microsoft.com/en-us/windows/win32/intl/ime-hot-key-identifiers) [Windows IME 알림 API](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immnotifyime)

검수용 분리 창을 SDL로 옮겼을 때 Win32의 창 내부 원점은 화면의 `(816,514)`에서 `(880,514)`로 바뀌었다. 이동한 창에서 실제 `한`을 다시 조합하고 후보 목록을 요청했다. Windows는 창 내부 후보 위치 `(11,102)`를 반환했으며, 목록 수는 0이고 화면에 후보창은 나타나지 않았다.

같은 Microsoft 입력기 `0412`의 Win32 기본 `EDIT` 컨트롤에 실제 `g k s`를 입력하고, 조합 문자열이 2바이트일 때 같은 두 변환 요청을 비교했다. 두 요청은 성공값을 반환했고 `한`이 확정됐다. 요청 직후와 300 ms 뒤 모두 후보 목록은 0개였다. 별도 SDL 검수본에서 `SDL_HINT_IME_IMPLEMENTED_UI`를 `none`으로 바꿔 Windows 기본 입력 UI를 사용했을 때도 후보 목록과 후보창이 나타나지 않았다. 통상 입력 경로를 검수하려면 실제 한자 키 또는 Windows 입력기 메뉴에서 후보창을 연다. [Win32 입력기 메시지](https://learn.microsoft.com/en-us/windows/win32/intl/ime-messages) [SDL 입력 UI 설정](https://wiki.libsdl.org/SDL3/SDL_HINT_IME_IMPLEMENTED_UI)

## 본창의 실제 Microsoft 한자 후보창과 확정

Windows 11 Pro x64의 시제품 SHA-256 `93db62feb0043406e9854dccc016233ea9b06d14e90a536f8e3a0b901d80b346`에서 본창 메모에 조합 중인 `한`과 Microsoft 입력기의 후보창을 확인했다. 150% 화면의 본창 캡처에서 메모 캐럿은 대략 `(546,111)`, 후보창 왼쪽 위는 `(544,140)`이었다. 첫 후보는 `韓`이었다.

운영체제에 숫자 `1` 키를 보내 고르자 후보창이 닫혔다. UI Automation의 메모 값에는 `韓` 한 글자가 있었고 화면에는 대체 문자가 표시됐다. Windows 시스템 글꼴 Malgun Gothic에는 `韓`과 `漢`이 있으며 기존 시제품의 글꼴 범위는 이 둘을 포함하지 않았다.

분리 창을 열어 `g k s`를 보내 실제 두벌식의 `한` 조합을 별도로 확인했다. 자동화 도구의 오른쪽 `Ctrl`로는 후보창이 열리지 않았다. 이때 분리 창의 후보창은 열지 못했다.

Windows 글꼴에 한자 통합 및 호환 범위를 병합한 실행 파일의 SHA-256은 `9f98e43be9f7d9b6195efcad2765813e1535c83f26b20d2fd4cd031c745eb194`다. UI Automation으로 메모 값에 `韓漢`을 쓰고 본창과 분리 창에서 두 글자가 화면에 모두 보이는 것을 확인했다. 이 표시는 UI Automation으로 입력한 표본이며 위의 실제 IME 후보 선택과 별개다.

## 분리 입력 창의 실제 Microsoft 한자 후보창

한자 글꼴을 보완한 시제품을 Windows 11 Pro x64의 150% 화면에서 실행했다. 분리 창 원점이 화면 좌표 `(816,514)`일 때 물리 한자 키로 `한`의 후보창을 열었다. 분리 창 캡처에서 후보창 왼쪽 위는 대략 `(4,86)`으로, 메모의 왼쪽 입력 위치 바로 아래였다. 첫 후보 `韓`을 숫자 `1`로 선택하자 후보창이 닫히고 메모 화면과 UI Automation 값에 `韓` 한 글자가 남았다.

제목줄을 드래그해 분리 창을 `(1036,514)`로 220픽셀 옮겼다. `F6`으로 메모에 초점을 준 뒤 실제 Microsoft 두벌식으로 `한`을 다시 조합했다. 확정 메모 값은 비어 있었다.

이동 후 사용자가 제공한 화면에서 Microsoft 후보창이 새 입력 위치에 열렸다. 같은 이미지 안에서 캐럿은 대략 (149,237), 후보창 왼쪽 위는 (148,280)이었다. 후보창의 왼쪽 끝이 새 캐럿과 거의 같은 가로 위치였다. 후보창이 열린 이미지를 확인한 뒤 현재 창의 화면 원점도 (1036,514)로 확인했다. 분리 창을 Alt+F4로 닫자 창이 제거됐고, UI Automation 초점과 확인 당시 메모 값 '한'이 본창에 돌아왔다.

실제 Microsoft 두벌식 조합과 확정, 취소, 본창 및 분리 창의 후보창, 이동 후 후보창 위치와 초점 복귀를 확인해 Windows 1단계 수용을 완료했다. 사용자 화면에서 확인한 후보창과 합성 SDL 시험 결과는 별도로 기록했다.

## 분리 창의 제목줄 이동 진단

별도 진단본에서 분리 창의 빈 제목 영역을 클릭한 뒤 수평으로 드래그했다. SDL에 왼쪽 버튼의 누름과 이동 및 놓음이 전달됐고, ImGui에서 해당 창을 이동 중으로 인식했다. 화면에서 분리 창의 원점이 `(816,514)`에서 `(1036,514)`로 바뀌었다. 진단을 넣지 않은 기존 SHA-256의 시제품에서도 같은 방식으로 같은 두 좌표 사이의 이동을 확인했다.

이동한 분리 창에서 `F6`으로 메모에 초점을 준 뒤 Windows에 글자 키를 보냈다. `GKS`가 확정됐고 해당 값은 분리 창의 UI Automation에서 읽혔다. `Alt+F4`로 닫으면 분리 창이 사라지고 본창 메모에 UI Automation 초점과 같은 값이 돌아왔다. 이전 시도에서는 드래그 후에도 원점이 `(816,514)`였고, `Alt+Space`에서 이동용 Windows 시스템 메뉴는 나타나지 않았다.

## 2단계에 사용할 B0 자료

공개 `r1-rc10`의 Setup.exe를 수신하고 PE 메타데이터에서 내장 `studio.zip`을 추출했다. 설치 파일과 내장 ZIP의 SHA-256이 431과 일치했다. 기존 내부 묶음 검증기로 배포 파일 1,191개와 소스 개정 `6fd0991`을 대조하고 별도 폴더에 풀었다. 추출한 GUI의 SHA-256도 일치했고, 배포 소스에서 `python -m rfad --help`의 `serve` 명령을 확인했다.

현재 PC의 저장소와 사용자 자료 폴더, 기존 Studio의 작업 영역에서 고정 보존 ZIP 및 동결된 프로젝트 ID를 찾지 못했다. B0 보존 ZIP은 자료 미확보다. 동결 자료의 재생은 431의 SHA-256과 일치하는 ZIP을 확보한 뒤 별도 작업 사본에서 실행한다. Windows 기능 이식은 보존 브랜치와 최신 공개 RC10 설치본을 기준으로 계속한다. [공개 RC10 설치 파일](https://github.com/EIDOSDATA/TraceWave-Studio/releases/tag/r1-rc10) [B0 보존 묶음과 복원](430_알원_비제로_기준선_확정.md) [리팩토링 작업 순서](../09_개발계획/07_현행버전_완료후_리팩토링.md)

GitHub Actions의 보관 아티팩트는 0개였다. 로컬 자료에서는 431의 보존 ZIP, 작업 영역, 해시 목록과 공개 API·MCP 원본을 고정 크기와 SHA-256으로 검색했으나 일치 항목이 없었다. 실제 ZIP을 확보하면 검증과 작업 사본 두 개의 생성을 한 번에 실행할 수 있도록 복원 도구를 추가했다. 임시 파일 850개를 넣은 모의 ZIP으로 명령행 복원을 포함한 7개 시험을 통과했다. 기존 출력 보존, 손상된 ZIP·프로토콜 파일 거부, 파일 수 불일치 및 Windows 대소문자 충돌을 대조했다. 공개 RC10 설치 파일을 보존 ZIP 인수로 넘긴 별도 시험에서는 고정값 불일치가 보고됐고 출력 경로가 생성되지 않았다. [비교 작업 사본 복원 절차](430_알원_비제로_기준선_확정.md#비교-작업-사본-만들기)

## 새 클라이언트의 공개 명령 재생

`origin/WxWidgets`의 수용 개정 `781fdcc`에서 분리 작업 트리를 만들었다. 그 `Code` 트리 객체 `3d32b6bb1b9b982eead3652be76d601a444a864d`는 `r1-b0`와 일치한다. 보존 브랜치의 커밋 이력에서 도달 가능한 Git 객체 15,145개를 대조했다. 431의 보존 ZIP이나 작업 영역, 원래 공개 API와 MCP 기록에 해당하는 크기의 blob은 없었다. 이 PC 사용자 폴더와 D 드라이브의 해시 검색도 일치 항목이 없었다. | 자동 회귀 | Windows 창의 합성 SDL 시험은 5회 연속 통과했다. PCB 해석, 해석 작업과 조건의 Python 회귀 36건 중 35건이 첫 실행에서 통과했다. 남은 게시 경쟁 시험은 모의 작업자 시작을 5초 안에 확인하지 못했고 단독 재실행에서 통과했다. |

다음 작업은 여러 과거 RF 결과 중 하나를 선택하고 당시 개정, 출처와 S11 표본을 확인하는 것이다. 그 뒤 남은 출력, 84개 시안별 작업과 Windows 설치 후보를 검수한다. 다중 포트 작업의 실제 Windows 화면 검수도 진행해야 한다. B0 보존 ZIP을 확보하면 동결 작업 영역의 대조를 재개한다.

## 후속 플랫폼 검수

Windows에서 기능 이식과 배포 검수를 마친 뒤 Linux Vulkan의 X11·Wayland와 macOS Metal을 순서대로 실제 데스크톱에서 확인한다. Wayland는 기본 창 내부 도킹부터 검수한다. 이번 시제품 시험에서 등록된 WSL Ubuntu의 가상 디스크와 macOS 실행 장비는 확보되지 않았다. Linux 데스크톱의 Vulkan과 X11·Wayland, Metal을 지원하는 Mac을 확보하면 해당 플랫폼 검수를 진행한다.
