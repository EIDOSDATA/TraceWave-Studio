# Windows 서비스 응답 도착 처리 검증

2026-11-21 KST. 완료 계획 12번의 F0/F1/F4를 검증했다. Python 프로토콜 응답이 빈 수신 큐에 들어오면 Studio의 wx 이벤트 루프에 알린다. 응답과 로그는 기존 수신 큐, 제한과 요청 ID를 사용한다. 타이머는 남은 수신 항목, 기한, 작업 상태와 로그를 계속 확인한다. 종료를 시작할 때 도착 알림 연결을 해제한다.

| 실제 Windows Release 시험 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 시작 warm 각 20회, 첫 화면 p95 | 1.70초 | 1.74초 |
| 시작 warm 각 20회, 편집 준비 p95 | 2.79초 | 2.93초 |
| 10만 건 표 35초, 첫 행 자료가 화면 입력 시점에 없던 경우 | 242 / 2208 | 112 / 2230 |
| 같은 표의 합성 간격 p95 | 25.81 ms | 25.42 ms |
| 실제 WSL2 취소, 버튼 반응 | 22.36 ms | 19.87 ms |
| 실제 WSL2 취소, Studio 접수 관찰 | 184.80 ms | 128.71 ms |
| 실제 WSL2 취소, 서비스 수신에서 송신 | 109.18 ms | 108.92 ms |

표 계측은 조건별 한 번 실행했다. 서비스 도착 알림을 사용한 표에서 저장 및 재열기, 10만 건 전체와 마지막 행, 한글 필터를 다시 확인했다. 해석은 같은 격리 Python 소스와 동일한 openEMS 원문에 시험 로그 약 1000행/초를 결합했다. 취소를 한 번씩 실행해 guest 종료 확인, 이전 결과 보존과 재열기를 확인했다. 변경 후 실제 종료 확인은 입력 후 1532.81 ms였다. 표와 취소는 관찰한 사례를 보고하며 반복 지연 표본 전체를 수용한 판정은 남는다. [원시 실행 기록](136_서비스응답_윈도우_도착처리실행기록.json)

시작 p95는 두 실행에서 1.5초/2초 목표를 초과했다. 표 60 fps와 별도 재부팅 후 첫 실행 5회도 미확립이다. 변경은 열린 작업 중 조회 및 취소 응답 지연을 줄이기 위해 적용했다. 부팅 계측 기록 판독, 서비스 종료·로그 폭주·저장 복구·PCB 검색·과거 결과를 포함한 Windows 통합 회귀 15개와 CTest 13개가 통과했다.
