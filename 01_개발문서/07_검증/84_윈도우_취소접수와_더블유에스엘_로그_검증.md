# Windows 취소 접수와 WSL 로그 검증

2026-11-20 KST. 완료 계획 12번 F4의 Windows 취소 처리와 WSL 프로세스 수명을 확인했다.

## Windows 저장소와 취소 접수

저널은 읽을 때 pointer, manifest, 상태 파일의 바이트와 SHA256을 검증한다. 상태를 변경할 때는 검증을 마친 기존 바이트와 새 상태를 한 번씩 비교하고, 준비된 새 바이트를 그대로 게시한다. 접수 결과의 사본과 같은 commit의 영수증을 유지한다. 이미 처리한 요청 키를 다시 보내는 경우 새 commit을 만들지 않는다.

Windows 수신 시험이 남긴 저장 상태에 활성 해석 작업 한 개를 추가했다. 별도 표본은 완료 작업 사본 128개를 더해 저널 상태 크기를 늘렸다. 기존/개선 구현을 교대로 각 20회 실행했다. 작업 상태 변경과 접수 영수증을 모두 디스크에 쓴 시점까지 측정했다. 각 조건의 저장 바이트와 재실행 결과가 구현 간 일치했다.

| 입력 저널 크기 (bytes) | 첫 접수 p95 기존 / 개선 (ms) | 같은 요청 재전송 p95 기존 / 개선 (ms) |
| ---: | ---: | ---: |
| 67778 | 100.18 / 85.73 | 20.73 / 12.68 |
| 463719 | 313.58 / 173.88 | 143.13 / 92.89 |

위 표의 활성 작업은 저장소 처리 시간을 재기 위한 입력이다. 실제 Windows Studio에서 PCB 해석을 실행해 취소하고 이전 결과를 재열기하는 별도 시험을 두 차례 수행했다. 저널 변경만 반영한 실행은 버튼 상태 변경 22.57 ms, 서비스 접수 199.30 ms, 종료 관찰 1381.55 ms였다. WSL 회수 변경도 반영한 실행은 각각 24.47 ms, 243.26 ms, 1551.17 ms였다. 실제 접수 표본 중 하나는 200 ms 목표를 초과했다. [실행별 수치](85_윈도우_취소접수와_더블유에스엘_로그_실행기록.json)

## 같은 WSL 감독 경로에서 고속 출력과 종료 확인

WSL2의 일반 감독기와 설치된 Python을 사용해 시험 worker가 초당 약 1000행의 출력을 생성했다. 새 session으로 이동한 후손이 stdout과 stderr를 상속한 조건에서 최초 시험은 종료를 확인한 뒤에도 출력 회수 기한을 넘겨 `failed`를 반환했다. 원래 작업 그룹을 회수한 직후, 작업별 nonce를 상속한 후손을 확인해 종료하고 출력을 읽는 스레드의 완료를 기다리도록 순서를 바꿨다. 원래 사용하던 PID 시작 시각 검증과 독립 watchdog을 유지한다.

수정 후 3회 모두 2000행을 약 2초에 쓰고, 추가 출력 중 취소했다. 각 실제 실행에서 `cancelled`, 종료 확인, 동일 cursor 재접속, 16 KiB 로그 tail 상한과 미게시 상태를 확인했다. 첫 WSL 제어 응답은 126.40~155.38 ms였다. PCB 해석의 실제 Windows 작업에는 시험 로그를 주입하지 않았다. 고속 로그 시험은 WSL 감독기와 worker 수명을 검사하며, 실제 해석에서 같은 로그 부하를 가한 Windows 반복 p95와 전체 F4 수용은 남는다.
