# Windows 런처 종료 후 WSL 해석 작업 재접속

2026-11-23 / Windows 개발 PC, WSL2 TraceWave-Dev

## 기존 검수에서 작업 시작을 놓친 원인

실제 WSL 시험 네 개 중 세 개는 통과했으나 런처를 강제 종료하는 시험 하나는 worker를 발견하지 못했다. 이 시험만 입력 복사와 동시에 10초 카운트다운을 시작하고 시작 응답을 버렸다. 기한에 도달하면 정리 단계가 원래 Windows 런처를 종료했다.

실패한 실행 `8770e53a-6d3a-4d05-a441-9101fce1ecf6`에서 337개 파일 중 148개만 지정된 크기로 복사됐고 supervisor가 소유권을 인계하는 `handoff.json`과 worker PID가 없었다. 10.45초에 guest가 `startup_owner_lost`, `not_started`와 종료 확인을 기록했다. 같은 묶음의 성공한 두 시험에서 입력 337개를 복사한 뒤 소유권을 넘긴 시각은 각각 23.204초와 25.024초였다.

## 수정한 검수

제품과 같은 실행 환경 준비, 입력 목록 및 supervisor의 해시 대조를 사용한다. 시험용 Windows 런처는 WSL의 실제 시작 응답을 내보내고 연결을 유지한다. 검수는 전송 상한 안에서 응답을 읽어 프로토콜, 실행 ID와 nonce를 대조한다. 이후 별도 시작 확인 시간 안에서 guest가 공표한 실제 worker PID를 확인한다.

Windows 런처가 여전히 실행 중인 시점에 강제 종료하고 비정상 반환을 확인한다. 같은 guest에 다시 연결해 PID가 동일하고 작업이 아직 살아 있는지 확인한 뒤 해당 작업에 취소를 요청한다. guest의 계산 예산과 lease는 유지한다. [제품의 입력 전송과 실행 기한](400_해석작업_인계와_실행기한_검증.md)

## 실제 Windows와 WSL2 결과

- 런처 강제 종료 시험 `91eed187-b24e-41ef-9940-91b9633add9d`은 337개 파일의 전송과 소유권 인계에 13.470초가 걸렸다. 시작 응답을 받은 뒤 PID 479를 관측했다. Windows 런처가 비정상 종료한 뒤에도 같은 PID가 살아 있었고, 명시적으로 취소한 뒤 guest는 `cancelled`와 종료 확인을 기록했다.
- 같은 고정 소스에서 고속 로그 출력과 후손 취소, 런처 강제 종료와 재접속, 2초 guest 시간 초과, 정상 결과의 해시 및 내용 대조를 포함한 실제 WSL 시험 4개가 93.781초에 모두 통과했다. Windows 호스트의 전송 및 소유권 회귀 16개는 0.645초에 통과했다.
