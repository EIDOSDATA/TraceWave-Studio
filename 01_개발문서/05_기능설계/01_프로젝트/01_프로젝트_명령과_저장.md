# 프로젝트 명령, 저장과 스냅샷 0.2

제목의 0.2는 서비스 profile `rfad.projects/0.2`다. 현재 프로젝트 쓰기 schema `rfad.project/0.6`, 공개 envelope `rfad.api/2.0`과 별도로 버전 관리한다. 0.5의 선택적 기판/도체 이름은 [객체 이름 계약](../02_설계편집/14_객체이름과_표시계약.md), 0.6의 선택적 PCB 기계/제조 원본과 수입은 [PCB 교환 계약](../05_출력교환/05_기판형상과_제조파일_교환.md)을 따른다.

[일반 프로젝트 연구](../04_해석결과/05_프로젝트_연구화면.md)의 정의/진행은 프로젝트 원본과 분리한 workspace의 studies 목록과 불변 파일로 보존한다. 기존 workspace에는 목록을 추가하고 프로젝트 schema/명령/현재 revision/저장 기준/undo/redo는 변경하지 않는다. 생성은 원본 snapshot과 설정/전체 계획을 같은 transaction으로 등록하며 request key 영수증을 재사용한다. 재시작 시 미완료 연구는 중단으로 표시하고 자동으로 새 solver 작업을 만들지 않는다.

이 구현은 RFAD-D0-3.4의 API-002~006, FN-001/002, SYS-036, PRJ-006/007, NFR-004 및 VT-018 일부를 구체화한다. 현재 이름/설명, 리터럴/표현식 매개변수, 기판/재료/적층/도체/net/단일 포트와 목적별 입력 검사를 지원한다. 필드는 [설계 데이터](../../02_시스템명세/09_표현식과_설계데이터.md)를 따르며 0.3에서 [목표 입력](../02_설계편집/06_대역목표_입력계약.md), 0.4에서 [목표 제약과 설계 규칙](../02_설계편집/11_목표제약과_연결_설계규칙검사.md)을 추가했다. [적층과 외부 환경](../02_설계편집/12_적층과_외부환경.md)은 별도 버전의 프로젝트 확장이다. 선택 속성 편집과 영속 undo/redo는 [편집 확장 profile](../02_설계편집/02_속성편집과_실행취소.md)로 연결했다. 전체 CAD 형식, 범용 migration, 임의 이력 이동과 전체 VT-018 완료를 뜻하지 않는다.

## 실행과 지원 범위

Code에서 실행한다.

```powershell
$env:PYTHONPATH = 'src'
python -X utf8 -m rfad serve --workspace .local/projects-workspace
```

`--workspace`가 있으면 `rfad.projects/0.2` profile을 제공한다. 없으면 기존 읽기 전용 `rfad.bootstrap/0.1`을 유지한다. workspace는 프로젝트 상태와 접수 이력을 함께 관리하는 로컬 서비스 저장 영역이다. 같은 workspace의 두 번째 writer는 E_CONFLICT로 거부한다.

| API | 현재 지원 | 응답 |
| --- | --- | --- |

project.open의 일반 copy, 외부 독립 프로젝트 import, 다른 target으로 저장, archive/migration/GC는 아직 지원하지 않는다. `sweep.selection.*`의 새 사본은 완료된 `grid_sweep` 후보의 리터럴 매개변수와 지원된 원본/자료 복사에 한정한다. 원본 프로젝트의 current/saved/undo를 변경하지 않으며 모든 프로젝트와 실행 이력을 이관하는 일반 copy 완료를 의미하지 않는다. recover는 현재 journal의 정상 pointer와 hash를 검증해 다시 여는 모드다. 손상된 파일을 임의 수정하거나 과거 revision을 자동 선택하는 복구는 수행하지 않는다.

새 프로젝트에는 project/revision/world/board의 별도 UUID와 오른손 identity 좌표계, 빈 컬렉션을 만든다. 지원 설계 객체, 목표, 기대 연결과 제조 규칙은 명시적 명령으로 편집한다. 새 문서는 rfad.project/0.6이며 0.1~0.5 원본을 그대로 읽고 다음 편집의 새 개정을 0.6으로 전환한다. 전환 응답/command journal의 schema_migration에 from/to/original_revision을 남기고 기존 봉인 bytes/hash를 유지한다. 기판/도체 name, pcb와 board.cutouts는 선택 필드이며 읽기나 관계없는 속성 편집으로 만들지 않는다. PCB 편집 역명령은 원래 컨테이너의 부재까지 복원한다. 미지 extensions의 JSON은 그대로 보존한다. [목표 제약과 설계 규칙](../02_설계편집/11_목표제약과_연결_설계규칙검사.md)

PCB 선택은 알려진 `extensions["rfad.pcb-selection"]`에 원문 사본과 채택 근거를 저장한다. `pcb.selection.apply`는 현재 개정과 검토한 미리보기 해시를 다시 확인한 뒤 내부 `pcb_stackup.apply` 한 명령으로 재료/적층/급전 좌표/출처를 변경한다. 일반 `project.apply_command`로 이 내부 명령을 호출하여 검토를 우회할 수 없다. 기존 영수증 transaction과 undo/redo를 재사용하고, 설치 카탈로그가 없어도 저장된 선택과 snapshot을 읽을 수 있다. 상세 계약과 출처 보존 한도는 [PCB 선택](../03_재료/02_기판선택과_적층적용_계약.md)을 따른다.

## 명령과 재전송

구현은 공개 `ProjectService`를 유지하면서 책임별 객체를 조합한다. 저장 schema와 JSON-RPC 응답은 이 분할로 변경하지 않는다.

| 모듈 | 책임 |
| --- | --- |
| [projects.py](../../../Code/src/rfad/application/projects.py) | 공개 API, 기능별 명령 분배, 자료 처리 worker 수명과 CAD/solver 연결 |
| [project_contract.py](../../../Code/src/rfad/application/project_contract.py) | 요청 필드/UUID/경로 검증과 초기 저장 예산 |
| [project_repository.py](../../../Code/src/rfad/application/project_repository.py) | 실제 소비할 불변 바이트와 문서 검증, 새 revision 저장, 프로젝트 참조 조회 |
| [project_history.py](../../../Code/src/rfad/application/project_history.py) | 명령/역명령, 이력 head, undo/redo와 구버전 이력 복원 |
| [project_operations.py](../../../Code/src/rfad/application/project_operations.py) | open/save/snapshot 및 입력 검사 작업의 실행 |
| [request_ledger.py](../../../Code/src/rfad/application/request_ledger.py) | epoch와 receipt, 같은 키 재전송 및 원자 접수 |
| [job_state.py](../../../Code/src/rfad/application/job_state.py) | 허용한 작업 상태 전이와 단조 증가 event 기록 |

Repository/History/Operations는 별도 journal transaction을 중첩해 열지 않는다. RequestLedger가 명령 실행 callback과 receipt 기록을 같은 transaction으로 감싸므로 파일을 나누어도 명령과 ACK의 원자적 경계는 유지된다. 런타임 monkeypatch나 mixin으로 메서드를 조립하지 않는다. 기존 worker가 사용하는 `_load`/`_project`/`_event` 등의 연결 메서드는 명시적 위임으로 유지한다.

과거 이력이 없는 프로젝트만 한 번의 명령 색인으로 복원하고, 각 현재 revision은 한 번 읽어 검증한다. 현재 문서와 접수 시 captured 문서는 같은 canonical/hash 검사를 거친다. 지원하지 않는 자료 처리 작업은 E_UNSUPPORTED로 실패하며 snapshot 분기로 흘러가지 않는다. coordinator 시작 도중 실패해도 이미 시작된 자료 처리 thread를 종료하고 writer lock을 반환한다.

변경/접수 params에는 `contract_version`, `context`, `input`, `request_key`, `request_key_epoch`를 넣는다. wire 버전은 `rfad.api/2.0`이다. epoch는 capabilities.get에서 얻은 실제 UUID를 사용한다.

project.apply_command의 context는 project_id, input은 expected_revision/command_id/type/payload다. parameter.set의 payload는 id/name/quantity다. quantity.value_si는 이미 SI 값이므로 표시 단위의 배율을 다시 곱하지 않는다. command_id와 parameter id는 정규 UUID 문자열이다.

1. 현재 revision과 expected_revision을 비교한다. 불일치하면 E_CONFLICT다.
2. 원본 사본에 허용한 명령만 적용하고 전체 문서와 단위를 검사한다.
3. 새 revision UUID, 부모 revision, 변경 영향과 역명령을 기록한다.
4. 불변 project.json과 checksum을 준비한다.
5. current revision 참조, 명령 이력, receipt를 같은 journal commit으로 게시한 뒤 ACK한다.

같은 epoch/key/payload는 같은 결과 또는 TaskRef를 반환한다. 같은 키의 다른 method/context/input은 E_CONFLICT다. 동일 command_id를 새로운 request_key로 다시 적용하는 것도 거부한다. 무변경 재전송은 새 디스크 commit을 만들지 않는다.

metadata.set은 이름과 설명을 한 명령으로 적용한다. 일반 명령과 편집 확장의 변경 모두 프로젝트별 최근 128개 원명령 이력을 갱신한다. undo/redo는 과거 revision 포인터를 덮어쓰지 않고 새 revision을 게시하며 저장 기준점과 스냅샷을 유지한다. 이력 head와 현재 revision이 다르면 차단한다. 세부 호환성과 제한은 [편집 계약](../02_설계편집/02_속성편집과_실행취소.md)을 따른다.

후보를 새 작업 사본으로 채택할 때는 원본과 별도 프로젝트 ID/경로를 만든다. 새 사본의 연구 기준 개정을 준비한 뒤 내부 채택 명령 한 번으로 선택 값을 적용하고 채택 후 개정을 saved로 게시한다. 새 사본에서 undo 1회는 같은 새 ID/이름의 기준 사본으로 돌아가며, 원본 프로젝트를 바꾸거나 새 사본을 삭제하지 않는다. 일반 `project.apply_command`로 내부 채택 명령을 직접 호출해 검토를 우회할 수 없다. 파일 복사 범위, 출처 보존과 결과 불명 복구는 [후보 채택 계약](../06_연구/02_후보채택과_새작업사본.md)을 따른다.

epoch의 신규 접수 기간과 receipt 보존 기간은 각각 7일이다. 기존 receipt를 먼저 검사하므로 epoch가 끝나도 해당 receipt 자체의 expires_at 전까지 재조회할 수 있다. receipt가 없고 epoch가 만료/미인식이면 E_IDEMPOTENCY_EXPIRED다. 만료 뒤에는 원 작업/프로젝트를 조회하고 명시적으로 새 요청 여부를 정한다.

## 비동기 자료 처리

open/save/snapshot/design.validate는 실제 background thread에서 순차 실행하며 짧아도 접수 응답을 최종 결과로 바꾸지 않는다. TaskRef에는 job_id/state/events_cursor를 넣는다. queued -> running -> completed 또는 failed를 영속 event로 기록한다. event는 단조 증가 seq, run_id, timestamp, phase와 불확정 진행 상태를 가진다. 현재는 job.status polling으로 읽으며 API-028 push transport는 아직 없다.

save/snapshot/design.validate는 접수 때 검증한 revision의 artifact를 붙잡는다. snapshot과 design.validate는 이후 편집이 발생해도 그 입력으로 생성한다. save는 완료 시 현재 revision이 바뀌었다면 E_CONFLICT로 실패하여 저장 기준점을 되돌리지 않는다.

취소와 완료는 journal의 같은 writer 경계에서 경쟁한다. 실제 파일 transaction이 진행되는 동안에는 중간 상태를 다른 writer가 변경하지 않는다. 파일 작업이 시작되기 전에 취소되면 실행하지 않고 cancelled로 확정한다. 먼저 completed/failed가 게시되면 늦은 취소는 그 terminal을 반환한다. native/WSL 프로세스 취소 구현으로 확대 해석하지 않는다.

장시간 solver는 이 파일 작업 transaction 안에서 호출하지 않는다. 별도 SolverCoordinator가 [해석 worker 계약](../04_해석결과/02_해석작업_계약.md)의 불변 접수/WSL 실행/결과 게시를 처리한다. guest 종료 확인 전에는 취소 완료나 자원 반환을 확정하지 않는다.

재시작 시 queued는 다시 처리할 수 있다. running은 완료를 입증하지 못하므로 interrupted로 남기며 자동 성공/재실행하지 않는다. 정상 동작 중 epoch 갱신은 실행 중인 작업 상태를 바꾸지 않는다. 종료는 현재 파일 transaction을 마친 뒤 worker와 writer lock을 해제한다.

## 저장 배치와 원자적 경계

```text
workspace/
  .writer.lock
  current.json
  commits/<commit_uuid>/
    state.json
    manifest.json
  projects/<name>/
    revisions/<revision_uuid>/project.json
    snapshots/<revision_uuid>/<snapshot_uuid>/project.json
```

초기 저장 profile은 08번의 current-revision pointer 방식이다. current.json이 지정한 검증 manifest/state가 현재 설계, 명시적 저장 기준점, 스냅샷, 명령/작업/receipt를 한 번에 확정한다. 각 revision의 project.json은 실제 설계 원본의 불변 바이트다. 별도의 가변 project.json과 receipt 파일을 각각 교체해 원자성을 주장하지 않는다.

따라서 이 초기 profile에서 프로젝트 하위 폴더만 복사하면 독립적으로 열 수 없다. workspace 전체와 current/commits의 참조가 필요하다. 독립 프로젝트 폴더/인계 archive는 추후 export/migration profile로 제공한다. 원본 역할과 저장된 값은 유지하며 이 배치 차이를 승인 문서의 완료 상태로 소급하지 않는다.

명령 적용 때마다 새 revision을 영속화하므로 서비스 중단 뒤 승인된 변경을 복원할 수 있다. project.save는 사용자가 명시한 saved revision을 별도로 확정한다. autosave draft/사용자 저장 기준점/실행용 snapshot을 같은 것으로 취급하지 않는다. autosave draft 자체는 아직 미구현이다.

게시 순서:

1. 새 immutable payload를 기록하고 flush/fsync 및 read-back 검증한다.
2. 새 state와 manifest에 byte 길이와 SHA256을 기록하고 검증한다.
3. 같은 volume의 임시 pointer를 기록한다.
4. current.json 하나를 마지막에 교체한다.

게시 전 실패는 이전 pointer와 정상 상태를 유지한다. 미게시 파일은 남을 수 있으나 결과로 노출하지 않는다. 게시 뒤 ACK 전에 실패했다면 오류에 `details.committed=true`를 남기며 동일 request_key로 확정 결과를 재조회한다. 읽을 때마다 pointer/manifest/payload와 프로젝트 artifact hash를 확인한다. 손상된 파일을 조용히 재생성하거나 덮어쓰지 않는다.

Windows에서 파일 fsync, 같은 volume 교체, 실제 프로세스 강제 종료와 OS lock 해제를 시험했다. WSL Linux의 ext4 임시 저장소에서도 저장/잠금/복구 시험을 통과했다. 정전/하드웨어 쓰기 cache 장애의 완전한 내구성은 아직 검증하지 않았다. [Python 파일 교체/동기화](https://docs.python.org/3.12/library/os.html), [Windows 파일 잠금](https://docs.python.org/3.12/library/msvcrt.html#msvcrt.locking)을 사용한다.

## 제한과 데이터 보존

- 프로젝트 경로는 workspace 안의 `projects/이름`이다. absolute/상위 이동/Windows 예약 이름과 기존 symlink/reparse 경로를 거부한다.
- create는 이미 존재하는 경로를 덮어쓰지 않는다. 미게시 orphan이 남은 경로도 자동 삭제하지 않는다.
- 프로젝트 512 KiB/32개, 매개변수 128개, 설계 객체 256개(512 KiB 제한도 적용), jobs 512개/대기 32개, receipts와 명령 이력 각각 2048개, snapshots 1024개, epoch 128개가 초기 상한이다.
- journal state와 단일 artifact의 최대 크기는 각각 8 MiB다. 초기 disk admission은 최소 16 MiB 또는 새 상태의 이중 기록에 필요한 여유 중 큰 값을 확인한다. 실제 기록 실패도 별도로 처리한다.
- 오래된 commit과 artifact의 자동 GC는 아직 없으므로 상한/공간 부족은 E_RESOURCE로 접수를 거부한다. 보존 이력을 몰래 삭제하지 않는다.
- mutation batch와 mutation notification은 실행하지 않는다. 조회 batch만 지원하며 변경에는 응답 ID와 영속 request key를 사용한다.
- stdout의 최대 프레임은 1 MiB다. 큰 프로젝트/배열의 chunk/artifact 전송을 지원하는 완료 profile이 아니다.

## AI/MCP와 EDA 연결 경계

GUI와 자동화는 같은 프로젝트 서비스 명령을 사용한다. [MCP adapter](../../../Code/src/rfad/application/mcp.py)는 MCP `2025-11-25`의 initialize, ping, tools/list, tools/call을 기존 공개 API에 연결한다. [stdio 진입점](../../../Code/tools/mcp_stdio.py)과 [시험](../../../Code/tests/test_mcp.py)이 있으며 revision/request key/job ID/snapshot을 별도 원본으로 복제하지 않는다. 내부 JSON-RPC 자체와 MCP transport는 구분한다. resources/prompts, 여러 외부 host의 상호 운용 수용 및 EDA 의미 변환 전체를 완료한 것은 아니다. 공통 경계는 [공유 계약](../../02_시스템명세/08_공통구현_계약.md)을 따른다.

다른 EDA 도구와의 연계는 AI host가 여러 MCP 서버를 조합하거나 별도 EDA 파일/데이터 adapter를 사용하는 방식이다. 각 도구의 단위/좌표/layer/net/재료/port 의미를 변환해야 하며 MCP 연결만으로 데이터 호환성을 보장하지 않는다. 이 문서 정리는 새로운 MCP/EDA 기능 구현이나 상호 운용 검증 기록이 아니다.
